# Операционный регламент админки «Проба Пера»

Этот регламент описывает production-действия после завершения разработки. Все
опасные операции выполняются только workflow из ветки `main`; ручное применение
SQL, публикация из локальной ветки и передача секретов в чат запрещены.

## Ежедневный контроль

1. Открыть **Состояние сайта**. Нормальное состояние схемы и публикации —
   `Исправно`; `Ограничено`, `Ошибка`, `Не настроено` и `Неизвестно` не считаются
   зелёным результатом.
2. Проверить очередь публикации. Рост очереди или более 50 неподтверждённых
   запросов требует проверки deploy workflow, а не повторного сохранения данных.
3. Просмотреть сгруппированные клиентские ошибки. Интерфейс скрывает токены,
   параметры URL и управляющие символы; секреты всё равно нельзя вводить в поля
   контента или диагностик.
4. Проверить последний запуск **Encrypted Supabase backup**. Успешный запуск
   означает: dump создан, архив зашифрован и расшифрован для проверки, Storage
   проверен по размеру и SHA-256 каждого объекта, а application schema реально
   восстановлена в изолированную PostgreSQL.

## Выпуск изменений

1. Получить зелёные точечные тесты и финальный CI pull request.
2. Слить проверенный PR в `main` и зафиксировать точный 40-символьный SHA.
3. Дождаться успешной резервной копии. Не продолжать при отсутствующем или
   повреждённом артефакте.
4. Запустить **Reconcile production database** с точным SHA и строкой
   `RECONCILE PRODUCTION DATABASE`. Workflow повторно сверит `main`, SHA-256
   миграций, выполнит изолированный restore drill и только затем применит весь
   план одной транзакцией.
5. Дождаться **Deploy editorial admin**, public deploy и live security audit на
   том же SHA. Финальная проверка — раздел **Состояние сайта** и один реальный
   цикл: черновик → сохранение → предпросмотр → публикация.

Нельзя перезапускать упавший reconciliation без анализа конкретного шага.
Checksum mismatch, неизвестная ledger-запись, ложный health-флаг или invalid
index являются блокирующими ошибками.

## Восстановление

1. Остановить редакционные публикации и сохранить SHA последнего исправного
   релиза.
2. Скачать только зашифрованный backup artifact и его `.sha256`; сверить хеш до
   расшифровки.
3. Сначала восстановить dump и UUID-only sidecar в изолированной Supabase
   PostgreSQL через `scripts/database/supabase-database-safety.sh restore-drill`.
4. Проверить Storage командой
   `node scripts/verify-supabase-storage-backup.mjs <storage-root>`. Любой
   отсутствующий объект, повтор пути, небезопасный путь, размер или SHA-256
   останавливает восстановление.
5. Сравнить количество статей, версию схемы, ledger, публикационные триггеры,
   health-флаги и отсутствие invalid indexes. Только после этого владелец может
   разрешить production-восстановление.
6. После восстановления заново выполнить health, smoke публикации и live
   security audit. Не удалять исходный зашифрованный артефакт до окончания
   проверки.

## Инциденты

- **Сохранение или публикация не работает:** не повторять действие много раз;
  сохранить incident/fingerprint, проверить схему и очередь публикации.
- **Конфликт версии:** обновить страницу и вручную сверить редакцию. CAS-защиту
  и блокировки обходить нельзя.
- **Перевод отклонён схемой:** исходный RU-контент остаётся неизменным. Исправить
  пакет через журнал перевода; не публиковать частичный EN-результат.
- **Ошибочный дизайн:** выпустить rollback в **Site Studio → Выпуски**. Не
  вставлять произвольный CSS/JavaScript и не менять owner-locked компоненты в БД.
- **Медиа отсутствует:** использовать обратимую корзину/восстановление или Safe
  Replace. Физическое удаление разрешено только владельцу после retention и
  повторной проверки всех зависимостей.
- **Подозрение на утечку:** отозвать соответствующий secret у провайдера,
  проверить GitHub/Cloudflare/Supabase audit logs и только затем заменить secret.

## Периодическая проверка

- еженедельно: MFA владельцев, состав команды, открытые ошибки и очередь;
- ежемесячно: ручной backup run и restore drill; первый backup месяца хранится
  90 дней, обычные ежедневные — 30 дней;
- перед крупным выпуском: CSV статистики, route/module coverage, Worker size,
  CSP/live security и проверка rollback Site Studio;
- после смены владельца: убедиться, что остался хотя бы один владелец. Все
  изменения ролей проходят только атомарные owner RPC.
