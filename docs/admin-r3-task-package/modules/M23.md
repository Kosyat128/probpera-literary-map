### M23. Загрузка файлов: граница HTTP, восстановление Storage и регистрация — P0/P1

**Основание.** Media Route Handler сначала разбирает multipart, а ограничение `File.size` проверяет уже после этого; разбор расположен вне его основной try/catch. В обоих просмотренных upload Route Handlers нет локальной явной проверки Origin, что требует проверки общей защиты, но не доказывает эксплуатацию production. MIME/размеры/пиксели и SHA-256 изображений уже проверяются. Шрифты адресуются по содержимому и намеренно не удаляются сразу при ошибке регистрации: файл может использовать другая конкурентная операция. [R2E10, R2E11]

**Граница запроса.** Отдельно проверить обычные Route Handlers: встроенные гарантии Server Actions не переносить на них по предположению. При cookie-auth защищать записывающие запросы согласно реальному origin/CSRF контракту проекта; принимать только проверенный собственный origin/разрешённый адрес, корректно обрабатывать proxy-host и missing/null Origin. Не считать произвольный X-Forwarded-Host доверенным. Сохранить legit same-origin upload для текущей конфигурации `ADMIN_BASE_PATH=/` и проверенного `/admin`, не включать широкий CORS wildcard и не требовать GET-мутаций. Проверить сторонний сайт и недоверенный sibling subdomain как разные случаи в изолированной среде.

Ограничить общий объём запроса, число полей/файлов и обработку до неограниченного буферизования там, где поддерживает runtime. Один Content-Length недостаточен: он может отсутствовать. Если runtime/adapter уже гарантирует hard limit, документировать и испытать его на фактическом Cloudflare/OpenNext preview, а не дублировать опасный парсер. Ограничения body/file/pixels/multipart overhead согласованы; client limit оставляет обоснованный запас, серверная граница остаётся окончательной. Ошибки multipart, неподдерживаемого MIME, повреждённых размеров, 413/415/422/429/503 дают понятный результат без сырого ответа провайдера.

Не ослаблять sniffing контейнера, ограничение пикселей, SHA, запрет SVG/GIF или удалённых шрифтов, если они действуют в текущем контракте. Не называть проверку заголовка полным антивирусным сканированием. Не загружать/не передавать сами шрифты в отчётный пакет. Если нужна дополнительная тяжёлая обработка, сначала оценить бюджет Worker и использовать существующий pipeline, не добавлять неограниченную декомпрессию.

**Восстановимая операция Storage + БД.** Одна SQL-транзакция не объединяет объектное хранилище и регистрацию. Сначала проверить существующие lifecycle/cleanup workflows. Расширить их минимальной записью операции/резервацией, устойчивой идентичностью запроса, состояниями prepared/uploaded/registered/failed/cleanup-needed либо эквивалентом. После обрыва различать сохранённый объект без записи, зарегистрированный файл без ответа и известный отказ. Retry сначала сверяет операцию и не создаёт копии без необходимости. Пользователю показать завершённые и неуспешные файлы по отдельности.

Компенсация учитывает тип адресации и ссылки: для нового случайного image-path допустима безопасная очистка своего неиспользуемого объекта, если принадлежность и отсутствие зависимостей подтверждены; для content-addressed font-path нельзя удалять общий объект из-за чужой ошибки регистрации. Cleanup имеет grace period, повторную проверку ссылок непосредственно перед удалением, журнал и ограниченные повторы. Упавшая cleanup не скрывается, но не выдаётся за провал уже принятой записи. Тестовые файлы не распространяют за собой real user data.

**Конфиденциальность.** Статус «черновик материала» не делает уже публичный Storage URL секретным. Проверить фактические bucket policies, использование подписанных ссылок и previews. Не переводить весь существующий публичный bucket в private и не ломать текущие изображения. Для действительно конфиденциального нового вложения нужен поддерживаемый изолированный режим; если его нет, явно не обещать приватность.

**Приёмка.** Защита работает на настоящем Route Handler; malformed/oversized запрос не валит обработчик; retries/crash recovery не теряют зарегистрированные файлы; конкурентная регистрация шрифта не удаляет общий файл; существующие изображения и публичные ссылки не изменены.

### Уточнение R3: контракт приватных ответов
[R3E07, R3E08, R3E10] No-store в успешной ветке конкретного API не доказывает те же заголовки у 401/403/503, redirect, malformed DTO или prefetch/RSC. Проверить итоговый ответ после реального middleware и deployment proxy, не только исходник отдельной функции. Если общая защита уже покрывает ветки, сохранить её и добавить тест, не дублировать конфликтующие политики во всех обработчиках.

Содержимое ошибок — безопасный код и correlation ID, без токенов восстановления, секретов или приватных payload. Проверку кеша проводить разными тестовыми аккаунтами; безопасный cache публичных ассетов не отключать из-за приватности admin JSON.
