### M04. Подтверждённая публикация, очередь и время — P1

**Основание.** public_build_outbox и экран requested/dispatched/deployed/failed уже есть. Досье, в отличие от статических материалов, доставляются через live no-store RPC и не требуют публичной сборки. Нельзя насильно переводить оба пути на одну технологию. [E08, E11]

**Реализация.** Общий UI состояния материала поверх двух адаптеров доставки: build-backed и live-backed. Различать сохранённый рабочий черновик, принятую к выпуску редакцию, ожидающую операцию и версию, доступность которой подтверждена по её реальному механизму. Git SHA недостаточен как идентификатор редакции контента.

Сопоставлять entityId + locale + revision/content fingerprint + operationId с release/snapshot manifest и успешным deployment. Один build может включать много изменений; поздний сигнал от старого build не должен отмечать новые редакции опубликованными. Проверку live-досье связывать с опубликованной редакцией/variant bank, а не с запуском Pages. В UI явно различать подтверждение доставки артефакта и отдельный live smoke на пользовательском адресе.

Сначала проверить существующие coalesce/head-check/экспортёры. При выпуске контента событие outbox и изменение публикуемой записи должны быть в одной транзакции там, где этого ещё нет. Черновик не создаёт публичный выпуск. Ошибка отправки внешнему deploy-провайдеру оставляет сохранённое событие для повтора. Сбой ответа после commit не должен создавать новую редакцию при повторе той же операции.

Идемпотентность, ограниченные повторы, backoff, защита claim/lease в транзакционном хранилище; не использовать KV как lock. Не обещать exactly-once внешней сети. Повтор для активной операции не порождает дубликаты; зависшую отличать по lease/heartbeat. Сборки объединять с учётом версии, а не терять промежуточные запросы. Не уничтожать историю outbox при очистке UI.

Добавить возраст очереди, последнее подтверждение, понятное имя материала, публичный адрес, ссылку на сборку и безопасный повтор конкретной ошибки. Ограничить статусный polling видимой вкладкой и активными задачами.

Время хранить в UTC; ввод и отображение используют явную IANA-зону. Сохранить существующую редакционную зону; при её отсутствии выбрать документированное значение Europe/Moscow с возможностью изменить до планирования. Зону браузера не применять молча. При вводе показывать дату, время, зону и UTC; отдельно обрабатывать неоднозначное/несуществующее местное время при смене DST. Date-only событие не преобразовывать в выдуманное время. Не менять уже запланированные instants. Интервал планировщика не выдавать за гарантию секунды публикации.

**Приёмка.** Тесты commit-then-timeout, двух вкладок, повторного webhook, старого build, нескольких изменений в одном build и независимой live-доставки досье; ни один успешный тост не утверждает непроверенную публичную версию.

**Уточнение R2 — обязательное сохранение действующих гарантий.** Повторный разбор SQL подтвердил транзакционные outbox-триггеры на 20 таблицах; обычный action не обязан создавать вторую транзакционную очередь. Отдельный trigger-event и explicit request-event намеренно могут сосуществовать. Нельзя deduplicate все pending строки по entityId, переиспользовать старый outbox ID или помечать новой редакции статус старого build. Отличать повтор одного пользовательского operationId от разных добросовестных событий. UI может группировать их без потери идентичности. Проверить сохранность при delayed commit и high-water mark экспорта, а также неизвестный результат mark_public_build_dispatched. [R2E16, R2E17]

Существующий экспорт уже повторяет обычный и Premium-снимок совместно и не публикует промежуточный hash. Сохранить это поведение и испытать, а не переписать exporter. Под «черновик не публикуется» понимается неизменность публичной редакции/публичного snapshot; допустимое внутреннее invalidation-событие для актуализации зависимостей само по себе не является утечкой. Не отключать durable triggers ради пустого outbox в тесте. Очереди рабочих autosave не должны автоматически выпускать контент. [R2E18]

### Уточнение R3: намерение повтора и валидный ID
[R3E04, R3E05] retryPublicationAction читает status, но сам не ограничивает deployed-состояние; UI-фильтр не является серверным контрактом. Разделить retry того же намерения и новый осознанный rebuild. Проверить терминальное/активное состояние и гонку между чтением и новой командой в устойчивой границе, сохраняя append-only outbox. Не удалять добросовестные row-trigger и explicit события ради требования «один повтор».

У любой межслойной команды ID должен быть проверен до следующего RPC: scalar UUID, объект результата, outbox bigint и revision token — не взаимозаменяемы. Нельзя допускать undefined ID и затем уходить в legacy queue как будто современной функции нет. Подтверждённая несовместимость сигнатуры, неверный DTO и временный сбой должны быть различимы от действительно неустановленной capability. Существующий fallback сохранять только в его доказанных границах совместимости, не выключать текущую защиту и не раздавать service-role.

Ошибку дополнительного audit/mark-dispatched после известного внешнего успеха не исправлять повторным вызовом провайдера. Показывать точный известный результат и необходимость reconciliation; реальная мутация и существующий trigger-event не должны исчезнуть из истории.
