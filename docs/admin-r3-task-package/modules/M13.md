### M13. SEO: полный список проблем по фактическому результату — P2

**Основание.** SEO-страница имеет редиректы и preview 12 статей с пустыми полями. Это проверка полей CMS, а не полная проверка опубликованного HTML. [E16]

**Реализация.** Переиспользовать scripts/audit-seo-release.mjs, audit-public-routes и прочие действующие проверки. Привести результаты к read-only отчёту с entity/path/locale, кодом проблемы, серьёзностью, проверенным release/snapshot, временем и ссылкой на редактор. Полный список с фильтрами/пагинацией; после исправления замечание закрывается только по новой проверке нужной версии, не по нажатию «Сохранить».

Различать raw CMS override и вычисленное значение. Пустой canonical_url не является автоматически отсутствующим canonical на публичной странице, если публичный renderer законно рассчитывает его. Предпросмотр обязан использовать тот же resolver, что и сайт. Проверять итоговые canonical, индексируемость, title/description/OG, sitemap, hreflang/языковые связи и JSON-LD по тем типам страниц, которые реально существуют.

Проверять циклы и цепочки редиректов, self-redirect, внутренние назначения и конфликты со старыми Tilda routes. Не менять slug/URL, robots, noindex или canonical массово без preview и отдельного редакционного решения. Не создавать новые публичные страницы из одной кнопки аудита.

Загрузка отчёта не запускает большой сканер синхронно в Worker. Хранить ограниченные данные/артефакт проверки с версией. Ошибка сканера или устаревший отчёт видимы. Исправления метаданных не переписывают статью и ручной перевод. Не генерировать «SEO-текст» автоматически и не обещать позиции поисковой выдачи.

**Приёмка.** Любое замечание можно найти и открыть; поля с корректным публичным fallback не получают ложную ошибку; старый зелёный отчёт не подтверждает новую сборку.

**Уточнение R2.** Смена taxonomy/page slug проверяется как связанное изменение URL, не только заполненность поля. Redirect-loop/цепочки/конфликт с существующим маршрутом должны блокироваться до выпуска; временные redirects и действительно внешние canonical не нормализуются автоматически по общей маске. Read-only HTTP-проверка URL подчиняется ограничению адресов/редиректов/таймаутов и не становится SSRF-прокси для произвольных введённых ссылок. Не скачивать весь интернет или платные отчёты ради SEO-панели.

### Уточнение R3: несовпадение RPC-результата и существующие SQL guards
[R3E11] create_seo_redirect_guarded в просмотренной SQL-миграции возвращает uuid. createRedirectAction передаёт `data.id` в requestRedirectBuild. При scalar UUID это undefined. Подтвердить фактическую сигнатуру на тестовой effective schema, воспроизвести полную цепочку создания и передать правильный валидированный ID. Предпочтителен минимальный адаптер вызывающего кода; не менять SQL на JSON-объект без анализа всех callers и совместимости.

Не путать этот дефект явного запроса публикации с потерей самого редиректа: штатные row-trigger/outbox могут сохранить underlying mutation. Ошибка уведомления/fast dispatch и существование canonical записи показываются отдельно. Обязателен DB integration test фактического возвращаемого значения, а не mock `{id: ...}`, который скрывает ошибку.

У redirect уже есть guarded RPC с advisory lock, CAS, проверками коллизий и транзакционным audit. Сохранять их. Проверить полноту сравнения эквивалентных внутренних адресов (same-origin absolute/root-relative), canonical fallback фактического renderer и legacy маршруты. Не удалять старые редиректы, не вводить blanket-normalization всех URL; публичная карта адресов и разрешённые external destinations сохраняются.
