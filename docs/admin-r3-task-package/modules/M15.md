### M15. Комментарии и управление командой — P2

**Основание.** Для pending-комментария индивидуальная кнопка предлагает скрыть; одобрение доступно через bulk. В списке материалов показан slug, в команде и истории — технические user ID. [E18]

**Реализация.** Для pending добавить отдельное «Одобрить»; для published — «Скрыть»; для hidden — «Вернуть», с текущим статусом. Прямая ссылка к материалу/контексту комментария строится безопасным route resolver. Отобразить причину модерации и понятный итог групповой операции, ограничить её размер и сохранить CAS по updated_at/revision. Не редактировать текст читателя вместо модерации, не скрывать комментарии за критику сайта как таковую.

Команда: понятное имя/email только для ролей, которым это разрешено; технический ID в деталях. Разрешённый серверный DTO не должен раскрывать auth.users целиком. Не расширять публичные профили ради отображения сотрудника. Дать описание прав каждой роли и текущего доступа.

Сохранить ограничения последнего владельца, назначения/отзыва ролей и аудита. Проверить гонку двух одновременных операций с владельцами на уровне БД, а не только заблокировать кнопку текущего пользователя. Отзыв роли должен закрывать новые защищённые операции, но не уничтожать авторство истории. Не добавлять незащищённый сброс чужого MFA из таблицы команды. Никаких настоящих приглашений, писем или изменений ролей при тестировании.

**Приёмка.** Ожидающий комментарий одобряется напрямую; bulk не теряет результаты конфликтов; последний владелец сохраняется при конкурентных запросах; сведения команды не доступны reader/guest.

**Уточнение R2.** Матрица прав в UI не должна расширять действующие серверные полномочия. Тестировать конкурентное удаление/понижение двух последних owner и повтор приглашения; ошибка БД не превращает список команды в пустой. Модерация затрагивает только выбранные IDs/versions, сохраняет причину и может вернуть ошибку по элементу без ложного сообщения об успехе всех строк. Редакторские настройки не меняют роль сообщества как побочный эффект.
