### M01. Единая проверка доступа и MFA — P0

**Основание.** В исходном auth.ts catch ошибки MFA создаёт checkError при required=false, а requireStaff не проверяет checkError. В layout проверяется required; отдельная страница новостей дополнительно проверяет checkError. PR #87 с DB-level opt-in MFA на момент подготовки открыт и является draft; наличие такого PR не означает применённую защиту в production. [E02, E03]

**Реализация.** Ввести или уточнить общий серверный результат доступа: разрешено / нет сессии / нет роли / требуется подтверждение MFA / проверка недоступна. Не полагаться на неизвестные или невалидные значения как на разрешение. Проверять действительную сессию, membership и MFA в каждой защищённой операции и при выдаче защищённых данных, а не только в layout. Скрытие меню и кнопок — дополнение, не защита.

Не менять добровольную политику подключения MFA на обязательную для всех. Staff без подтверждённого фактора работает по действующей opt-in-политике; staff с verified-фактором требует AAL2; ошибки чтения фактора/уровня не разрешают доступ. Сохранить доступ к login, MFA challenge, корректному logout и безопасному восстановлению без циклических редиректов. Запрос восстановления не должен раскрывать существование email.

Проверить роли по конкретным действиям, прямые RPC и Storage-пути. Не вводить общую restrictive-политику, которая случайно закроет чтение обычным читателям. Подготовить защиту в БД только после сравнения актуальных политик и PR #87; не cherry-pick/merge этот PR вслепую. SECURITY DEFINER: минимальный EXECUTE, проверка actor, квалифицированные имена и безопасный search_path. Не заменять пользовательский клиент service-role ради обхода отказов.

Не кэшировать авторизацию между пользователями. Отзыв роли и обновление фактора должны учитываться следующей операцией по фактической модели сессий. Проверить ошибку membership, просроченный токен, отсутствие конфигурации, прямое обращение к action/API и повторное выполнение в другой вкладке. Сохранять CSP, origin/CSRF-защиту, no-store/noindex и совместимость текущего Cloudflare/OpenNext runtime; не переносить middleware в другой runtime без доказательства совместимости.

**Приёмка.** Тестовая матрица guest/reader/editor/admin/owner × MFA отсутствует/нужен/подтверждён/ошибка. Запрещённые запросы не читают закрытый контент и не меняют БД; обычный читатель не теряет разрешённое публичное чтение. Для production-политик без доступа статус не «проверено».

**Уточнение R2.** Разделить авторизацию Server Actions и обычных cookie-auth Route Handlers; защита последних подробно в M23. Запрет выдачи закрытых DTO действует и для prefetch/RSC, export, preview, recovery и command-search. 401, 403 и 503 не использовать взаимозаменяемо там, где это меняет безопасный retry/UI; скрывать существование недоступного объекта согласно текущей политике. Не приписывать ошибке assurance доказанный обход production: проверка и исправление должны быть подтверждены фактическими backend-тестами.

### Уточнение R3: auth callback, восстановление и приватный кеш
[R3E08, R3E09, R3E10] Callback использует собственный safeNextPath и объединение с настроенным adminSiteUrl. Из этого исходника не установлена эксплуатация open redirect. Требуется явный контракт допустимой продолженной навигации, нормализации и basePath, без исполнения произвольной цели, попадания code/token в итоговый URL и зависимости от недоверенного Host.

Восстановление собственного пароля использует provider session/updateUser и signOut. Не заменяй его requireStaff в начале: это способно заблокировать восстановление. Проверяй поддерживаемое провайдером подтверждение личности/recency и MFA-политику, не создавая новую кастомную auth систему; не расширяй полномочия на изменение другого аккаунта. Проверить одноразовость/истечение ссылки и понятный повтор после отказа, без реальных писем в тесте.

Закрытые DTO нельзя выдать до auth guard, рассчитывая только на общий layout. После logout/account switch/back-forward BFCache и восстановленная вкладка не должны открывать содержимое прежнего пользователя. Политика сохранности ввода не означает перенос частного draft между аккаунтами. Сохранять штатный серверный Auth/SSR refresh; не объявлять cookie HttpOnly обязательным без проверки требований используемой SSR-библиотеки. Подтвердить безопасность и успешную работу действительной конфигурации, не навешивать несовместимые флаги вслепую.
