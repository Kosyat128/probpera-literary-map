### M18. Интеграционные тесты, миграции и пакет выпуска — P0/P1

**Проверки с начала работы.** Для каждого Mxx сначала воспроизвести проблему или подтвердить отсутствие, затем targeted unit/component/DB/browser tests. Source-string tests можно оставить как контракт, но они не заменяют проверку фактического поведения. Локальный browser mock не выдавать за проверку RLS; тест на service-role не доказывает права editor/reader.

Отдельный admin Playwright project/config с реальной админкой, изолированной БД и тестовыми owner/admin/editor/reader. Не использовать только публичный Vite-preview для доказательства работоспособности CMS. Playwright auth state/trace могут содержать секреты и закрытые данные: исключить их из Git/публичных артефактов, sanitize и минимизировать запись. Явно проверять, что baseURL/databaseRef не production.

Unit — парсеры/статусы/временные зоны; component — ошибки/dirty/focus; DB integration — RLS, CAS, транзакции, outbox и инварианты; admin E2E — вход, редактор, preview, restore, новости, книги, досье, медиа; public regression — отсутствие утечек черновиков и неизменность полки/глобуса/URL; release — существующие CI/build/size/schema checks. Объём и матрица в ACCEPTANCE.md.

**Миграции.** Сначала проверить существующие RPC и migration ledger. Новые изменения additive/forward-only, тестируются на чистой схеме и на копии прежней схемы с fixtures. Не редактировать уже применённые миграции. Не дропать таблицы/поля/политики массово, не делать reset remote. Новый код старой схемой не должен молча разрешать небезопасное действие: capabilities gate, graceful read-only.

Нужны план обновления, required capabilities, контрольные суммы, review allowlist по правилам проекта, пробный запуск и проверяемый recovery/backout без разрушительного down. Порядок выпуска определяется совместимостью конкретных изменений: совместимая добавочная схема → совместимый код → отдельное переключение чтения/публикации → проверки. При несовместимости схема/код готовятся отдельными контролируемыми стадиями, не «миграция всегда первой» без анализа. Старый опубликованный контент сохраняется.

**Финал.** По текущим scripts запустить обязательные проверки затронутых областей и полные gates для итогового diff. Перед запуском изучить побочные действия команд. В этом репозитории некоторые build цепочки вызывают экспорт/генерацию; использовать безопасный sandbox/snapshot, не потерять ручные данные и не сделать внешнюю запись. Не изменять проверку исключённой пунктуации. При её baseline-ошибке отчёт честно фиксирует блокер, без ремонта или ложного PASS.

Сформировать CHANGELOG/STATUS, ACCEPTANCE_RESULTS с фактической командой, SHA, средой, кодом завершения, датой и ссылкой на доказательство; список миграций и RELEASE_PLAN; список оставшихся блокеров; краткую инструкцию владельцу по новым действиям. «Реализовано» отдельно от «Проверено локально», «Проверено с БД», «Проверено в staging» и «Развёрнуто». Без production-доступа последний статус остаётся NOT_VERIFIED, а не выдумывается.

**Приёмка.** Обязательные тесты не пропущены молча; все изменения обозримы в diff; публичные данные сохранены; опасные внешние действия не выполнены без отдельного разрешения.

**Уточнение R2.** Закрыть также M19–M25. Все 26 блоков реализуются по применимости, но наличие исходников и этой спецификации не является PASS. Приложенный logic-reproduction содержит только независимые проверки нескольких JavaScript-выражений и не засчитывается за application unit/integration/E2E. Для каждого заявленного исправления минимум один воспроизводимый регрессионный тест, для каждого DB-инварианта реальные транзакционные тесты, для формы — браузерная проверка. Сверить чистую БД, upgrade с прежней схемы, старый код + добавочная схема, новый код + недостающая capability; откат к прежнему коду не должен открывать снятые доступы. Сборки выполняются в нужном runtime, не только Vite public preview. Финальный результат привязан к фактическому SHA/tree diff и среде.

### Уточнение R3: проверяемое завершение вместо роста отчёта
Состав базового задания остаётся M00–M25. R3 добавляет конкретные failure-mode проверки и уточняет реализацию, а не новую платформу. Для каждого подтверждённого code defect предпочтительно fail на исходном fixture/коммите и pass на исправленном; если воспроизведение старой ветки небезопасно/невозможно, это отмечается, не имитируется.

Проверить фактические формы результатов RPC по effective schema и валидаторам: scalar uuid, bigint/string, json object, set-of rows. DB mock обязан соответствовать контракту. Добавить тонкую contract matrix для затронутых функций; не переписывать все типы репозитория ради одного исправления.

IMPLEMENTED, VERIFIED_UNIT, VERIFIED_DB, VERIFIED_E2E, READY_FOR_REVIEW и PRODUCTION_DEPLOYED — разные поля, не одна зелёная кнопка. Результат каждого сценария связывается с command/exit code/env/code fingerprint/артефактом и применимым уровнем. Не смешивать логические воспроизведения этого пакета с application tests. Некорректная ссылка на evidence или неизвестная среда не закрывает приёмку.

Пересекающиеся сценарии разрешено покрывать одним содержательным тестом с несколькими IDs. В частности, M11-T02/M11-T07 относятся к близкому fail-closed контракту usage graph; не делать два одинаковых теста ради количества. Идентификаторы сохраняются для совместимости checkpoint, не выдаются за число уникальных выполненных автотестов. См. IMPLEMENTATION_CONTRACT.md и coverage equivalence.

Нет необходимости ждать реализации всей аналитики, чтобы получить полезный reviewable P0 diff. Но окончательный отчёт всей задачи обязан перечислить оставшиеся блоки, не менять scope молча. Фиктивные заглушки, «скоро», новые неработающие кнопки и обходы gates не закрывают модуль.
