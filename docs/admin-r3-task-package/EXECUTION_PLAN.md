# Порядок реализации и выпуск R3 FINAL

Это план для Codex. Приложение в рамках подготовки пакета не изменено. Номера M00–M25 — устойчивые идентификаторы, а не требование выполнять их строго по порядку.

## G0. Безопасная исходная точка

Прочитать AGENTS.md и CORE_RULES.md. Проверить git status/ветку/HEAD, незакоммиченные изменения, actual scripts/runtime и версии. Составить минимальный baseline M00 и изолированный admin test harness сразу. Не выполнять полный повторный аудит всех книг/картинок до первой правки. Не менять main и не стирать пользовательский diff. Проверить серверные зависимости на возможность безопасного тестирования без production.

## G1. Сохранность и граница доступа

Начать M01/M02 и M20: fail-closed MFA, истинные ошибки, dirty/receipt/recovery. M05 — общие редакторские guards; M19 — страницы и HTML/JSON. HTTP-часть M23 после M01/M02 не ждёт второстепенной аналитики или интерфейса. Для каждого исправления написать регрессионный тест на старое поведение, затем проверить исправленный сценарий. При доступной тестовой БД выполнить роли/ошибки/CAS. Нет тестовой БД — подготовить код и harness, явно оставить DB-сценарии BLOCKED и продолжить безопасные части.

## G2. Подтверждённые операции и системное состояние

M03/M04/M06/M07: общий смысл статусов, сохранение действующих outbox-триггеров и exporter, version-specific подтверждения, восстановление в draft, ошибки долгих задач. Не заменять append-only события coalesce по entity. Live-досье остаются live, статические материалы — по текущему build-протоколу. По завершении закрыть storage-registration часть M23 и накопительные дополнения M17.

## G3. Редакционные данные и безопасное управление

M08/M09/M10/M11; затем M21/M22/M24/M25 по зависимостям. Книги/издания/досье — существующий каталог, taxonomy — полная карта влияния, повестка — действующий блок без новостных articles. Не отключать досье-gates. Тексты сайта не зависят от удачи внешнего перевода для сохранности ввода. Социальные адаптеры тестируются mock-провайдерами, каналы не включаются автоматически.

## G4. Завершение ежедневных сценариев

M12–M16: рабочие ссылки, понятные группы меню, keyboard/focus, media, комментарии, команда, SEO/аналитика по реальному состоянию, согласованность Site Studio. В этот проход не включать редизайн публичного сайта, новый календарь, вторую энциклопедию и массовый контентный backfill.

## G5. Полная приёмка M18

Каждый затронутый сценарий уже имеет targeted проверки; теперь выполнить итоговые интеграционные, DB/RLS и admin browser проверки на зафиксированном diff. Не заменять admin Next/Cloudflare preview публичным Vite. Проверить отличия документации runtime и реально закреплённых зависимостей, не обновляя всё автоматически.

Проверить чистую тестовую БД, upgrade с прежней схемы, совместимость добавочной схемы со старым кодом, graceful read-only нового кода при недостающей capability, публичный export/права/полку/глобус. Использовать синтетические или разрешённые обезличенные fixtures. Внешние переводчики, социальные платформы и deploy API замокированы; это явно отмечено. Никакие state-файлы auth/cookies не попадают в commit.

## Границы миграций и production

Каждая новая миграция additive/forward-only, с контрольной суммой, ссылкой на требуемую capability и проверкой ledger по действующим правилам проекта. Исторические миграции не редактировать. Нельзя считать наличие файла доказательством применения. Проверку effective triggers/policies выполнять на тестовой схеме; в production — только чтение при уже имеющемся разрешении, без вызовов, меняющих данные.

Порядок будущего выпуска зависит от совместимости конкретной схемы и кода; не применять универсальное «всегда DB первой» без анализа. При switch источника новостей: зафиксировать master, экспорт/сверку, тест миграции, контрольный переключатель и план обратного переключения без потери новых правок. Не превращать rollback в удаление новой схемы/данных. Production deploy, migration apply, включение канала, реальная отправка и изменение реальных ролей требуют отдельного явного разрешения, которого этот пакет не даёт.

## Рабочий checkpoint

Использовать один существующий подходящий checkpoint проекта либо `docs/admin/STATUS.json` (или уже используемый checkpoint R2 без переноса). Поля: actual_head, branch, tree/diff fingerprint, current_module, завершённые/частичные/заблокированные пункты, команды и результаты тестов, затронутые файлы, следующий конкретный шаг. Не перезаписывать прежние completed без проверки, не хранить полные приватные тексты. Состояние пакета TASKS.json — начальная карта, не источник ложных выполненных работ.

Для продолжения прочитать checkpoint, текущий diff, CORE_RULES и только активный module-файл с его тестами. Не читать одновременно standalone TXT, ADMIN_SPEC и все modules: это альтернативные представления одного задания. На релизной границе повторить необходимые полные gates; после правки diff результаты затронутых тестов устаревают.

## Формат конечного результата Codex

Краткое резюме реализованного; ветка и актуальный SHA/tree; перечень изменённых важных файлов и миграций; ACCEPTANCE_RESULTS с ID/уровнем/средой/командой/датой/артефактом; защита данных и совместимость; оставшиеся BLOCKED/NOT_RUN; точный release/backout plan; инструкция владельцу для изменившихся операций. Отдельные статусы: IMPLEMENTED, VERIFIED_UNIT, VERIFIED_DB, VERIFIED_E2E, STAGING_VERIFIED, PRODUCTION_DEPLOYED. Последний не выставляется этой задачей без отдельного разрешения. Зелёная сборка не заменяет критерии приёмки.


## R3: ближайший вертикальный проход и контроль остановки

После M01/M02/M20 и защиты page editor выполнить адресные исправления:
1. M13 scalar UUID result + M04 validation до enqueue, с тестом реального SQL result. Не ждать всей SEO-аналитики.
2. M07 published freshness prefilter + attempts/deadline caps с mock-провайдером; затем стабильность scan/resume. Без массового перевода.
3. M05/M19 точная проекция preview и managed covers; затем M11 окно вставки >60 и DTO.
4. M01 callback/recovery и M23 приватные ответы в настоящем runtime; сохранить обычный recovery и существующие guards.
5. Остальные модули из исходного порядка по зависимостям. READY_FOR_REVIEW частичного P0/P1 diff не равен завершению всего пакета.

Перед каждым большим изменением проверь, нельзя ли закрыть defect текущим resolver/RPC/hook. В review сравни именно production-like форму ответа, а не удобный mock. Не добавляй универсальный workflow engine, новый Auth, новый uploader, вторую очередь или новую таблицу только для оформления отчёта.

Подробный report не нужен после каждого test-run: checkpoint содержит полный след, пользователю — фактическое исправление и важный блокер. Финальное сообщение кратко: что сделано, чем проверено, что не проверено, как безопасно выпустить отдельно. Никаких гарантий отсутствия будущих ошибок и расхода лимита Codex.
