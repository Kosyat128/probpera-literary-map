## Общие контракты, чтобы разделы не расходились

### Результат операции

Согласовать существующий тип и расширить его, если нужно:

- outcome: success / rejected / conflict / dependency-unavailable / unknown-outcome;
- operationId/correlationId и server revision при подтверждённой записи;
- fieldErrors для валидации; безопасный errorCode; retryable с конкретной семантикой;
- publicationState отдельным полем, не частью расплывчатого «успешно»;
- исходные значения не заменяются empty/default на ошибке.

Это не строгий новый API, который нужно внедрить во все файлы разом. Разрешены адаптеры для старых контрактов. Для GET ошибки HTTP/SSR и для Server Action формы обрабатываются подходящим существующей архитектуре способом.

### Версия и подтверждение

Любой audit/review/preview/release ссылается на конкретную редакцию. expectedRevision/updated_at проверяется сервером в момент записи; client role, hidden fields, raw JSON и отметка «проверено» не являются источником прав. Content hash для опубликованного snapshot не включает случайные временные поля и вычисляется детерминированно. Токены сравнения не теряют точность при передаче через JS.

### Авторские материалы и безопасность

Не превращать «сохранить без изменений» в массовое редактирование. Новый UI не генерирует содержание, не приводит имена/названия/источники к новым вариантам. При этом не отключать санитизацию небезопасного HTML: исходный безопасный контент и опубликованная проекция должны проверяться отдельными контрактами. Ранее существующее исключённое поведение учитывать только как точечный baseline, не как blanket-разрешение на изменения.

### Источники истины

Один master для каждого вида изменяемых данных. Snapshot/кеш/экспорт имеют явное происхождение и версию; недоступность master не даёт права перезаписать его старым snapshot. Не рассчитывать на синхронность KV между регионами. Канонические IDs книг/авторов сохраняются, а новые формы не создают локальные заменители.

## Дополнительные сквозные контракты R2 FINAL

### C01. Раздельные состояния одного изменения

У сущности могут независимо существовать локальный ввод, серверная автокопия, рабочий черновик, одобренная редакция, принятый запрос на выпуск, публичный snapshot/live-редакция и внешняя социальная публикация. Общая зелёная метка не заменяет эти состояния. Идентичность редакции не равна Git SHA; receipt принадлежит конкретной операции и набору данных. Текущий пользователь вправе видеть только разрешённые ему состояния.

### C02. Граница подтверждения

Подтверждённая сервером запись и неизвестный сетевой исход различаются. Восстанавливать результат запроса можно по устойчивому operationId с проверкой actor/entity/intent/expectedVersion; повтор с другим payload при том же ID отклоняется или явно конфликтует. Не хранить для этого бесконечные копии полных текстов в audit. `?saved=1`, число попыток и отсутствие ошибки в браузере не являются серверной квитанцией. Автоочистка требует доказанной принятой редакции; явный discard — отдельное намерение.

### C03. Outbox и целостность snapshot

Сохранить действующие after-mutation triggers, append-only события и совместный RU/Premium export. Идемпотентность команды не удаляет отдельные события разных транзакций. Нельзя подтверждать события по одному «последний ID» без проверки того, что снимок действительно их включает; проверить существующий high-water/content-hash протокол, особенно поздние commit. Группировка запросов в UI/одну сборку не уничтожает связь с исходными редакциями. Разрешённая внутренняя инвалидация от draft не равна его публикации.

### C04. Авторские тексты и представление

Никаких новых нормализаций, генераций или массового ремонта контента. HTML и JSON имеют согласованную безопасную проекцию и сохранённое происхождение. Утрата/повреждение одного представления — ошибка либо legacy-режим, не разрешение на пустую перезапись. Сохранить санитизацию; не переводить опасный HTML в разрешённый ради совпадения байтов. Исключение по дефисам/тире действует точечно и не допускает изменения смежного содержания.

### C05. Публичность не определяется видимостью кнопки

RLS/RPC/Server Actions/Route Handlers/Storage/preview/search/export проверяются отдельно. Закрытые drafts, источники прав и полный банк spoiler-вариантов не попадают в публичные payload/сборки/кеши. Наличие public URL файла означает отдельный режим доступа, даже если статья пока draft. CSS-hidden, noindex и подписанная надпись не являются контролем доступа.

### C06. Удаление и замена

Для каждой разрушительной операции определить dependencies, возможность восстановления и точные последствия до её выполнения. Версия и набор выбранных IDs входят в подтверждённое намерение; сервер проверяет их повторно. Никаких wildcard delete, молчаливого cascade или удаления shared content-addressed файла из-за ошибки другой операции. Soft-delete не обещает недоступность уже публичных внешних копий. Audit append-only, неоднозначный исход допускает reconciliation, не слепой повтор.

### C07. Источник истины и перенос

Один master на каждый тип данных. При переносе новостей/настроек есть baseline, проверяемый импорт, сверка количества/IDs/редакций, затем контролируемый switch и запрет двусторонних независимых записей. Snapshot не пишет обратно поверх master. Existing data, direct-card URLs и утверждённые публичные блоки не переносятся только ради новой структуры админки.

### C08. Время и срок действия

Точный instant хранится в UTC; значение с известным только днём хранится как date-only; неизвестная дата не подменяется текущей. Ввод времени имеет явную IANA-зону, валидный offset и обработку DST; не сдвигать ранее записанные instants. Срок прав/lease/self-test/backup применим к конкретному виду события и не обобщается одним TTL. Статус UNKNOWN не маскируется FAILED/OK.

### C09. Неподдерживаемые возможности

Не отключать gates, чтобы завершить форму. В частности, public dossier full-text/quote/media/articleReuse не включаются без необходимых уже одобренных прав и схемы; в проверенном снимке они запрещены. Канал социальной отправки без конфигурации не становится работающим. Capability-off не означает, что фиктивный успешный ответ допустим. Для новых независимых возможностей — явные состояния и безопасная интеграция, не неподключённая кнопка с обещанием результата.

### C10. Бюджет и исполнение

Сначала короткий baseline и P0, далее реализация вертикальными проходами: форма → action/API → DB/worker → обратная связь → регрессионные тесты. Не проводить весь повторный аудит прежде первого исправления. Каждая новая механика должна закрывать доказанный сценарий; не вводить event sourcing, CQRS, вторую очередь, тяжёлый графовый движок или внешний сервис без необходимости. Сохранить использованные runtime/версии dependencies, сначала проверить lockfile и commands. Наличие этой инструкции не делает выполнение бесплатным по лимиту Codex.

### C11. Доказательство завершения

У каждого теста есть ID, предусловия/шаги, ожидаемый результат, требуемый уровень и исходный NOT_RUN. Фактический результат отдельно содержит команду, дату, SHA/tree, окружение, outcome/exitCode, artifact и область mock. Source-string test не доказывает поведение DB или браузера; локальное выражение не доказывает работу production. BLOCKED/NOT_RUN/WAIVED с явным решением не считаются PASS. Смена diff требует повторной проверки затронутых сценариев. Не произносить «100% готово», пока не выполнены все применимые критерии.

### C12. Границы текущей задачи

Разрешена подготовка и реализация кода в безопасной ветке и изолированных тестах, но не production-мутации, включение отправки/платных вызовов или произвольный merge. Существующий доступ инструмента не равен разрешению на действие. При внешнем блокере продолжать независимый безопасный код и тесты; остановить только опасную часть. Задание окончательное по текущему обследованному объёму, а не гарантия отсутствия новых требований или будущих дефектов.

## Одно исправление — одна проверяемая цепочка
Для каждого модуля сначала выбрать текущий дефект/незавершённый сценарий, затем пройти UI → action/endpoint → RPC/storage → результат → проверка. Смена подписи без работающего backend, фиктивный success, кнопка «в разработке» и заглушка не закрывают требования. Не заменять реализацию документацией.

Для нового code defect фиксировать воспроизведение исходного поведения и исправленного на одинаковом fixture. Для существующего работающего механизма достаточно подтверждения поведения и сохранения regression test; не переписывать его ради другого стиля. Каждая заявленная исправленная ошибка имеет ссылку на конкретный diff и тест. Сам факт зелёной сборки не доказывает все сценарии.

## Формы данных между слоями
Фиксировать для затронутых RPC фактическую сигнатуру, returned SQL type, пример обезличенного результата, клиентский parser/DTO и callers. scalar UUID не row {id}, bigint не безопасный произвольный JS number, null не пустой успешный объект. Валидировать до следующего побочного действия. JSON parsing success не означает валидность бизнес-данных. Неподдерживаемый result возвращает безопасную ошибку и не даёт полномочий на compatibility fallback.

## Статусы и доказательства
TASKS.json и ACCEPTANCE_RESULTS_TEMPLATE.json в поставляемом пакете — исходный NOT_RUN. Они не описывают сделанные изменения приложения. Рабочие результаты вести отдельно с полями: test_id, status, code_fingerprint (HEAD + digest релевантного diff), environment, level, command, exit_code, checked_at, evidence_path, mocked_dependencies, limitations. Для DB/E2E PASS соответствующий dependency не замокирован. Скриншот без прохода action не доказывает DB; source substring не доказывает реальную функцию.

Допустимы NOT_RUN, RUNNING, PASS, FAIL, BLOCKED. NOT_APPLICABLE только с проверяемым архитектурным основанием и перечнем покрытого эквивалентного сценария; это не PASS и не способ исключить желаемую функцию. Для возможности, которой в текущем коде ещё нет, корректен PLANNED/BLOCKED, но не NOT_APPLICABLE из-за отсутствия реализации. Production/paid/social tests не выполняются без отдельного разрешения; вместо них подтверждаются безопасные локальные границы с явно указанным mock.

Близкие criteria могут ссылаться на один тест. M11-T02/M11-T07 — один failure family (unknown usage graph → no purge), сохранить оба ID в mapping для прежних checkpoint. Число criteria не является числом независимых автотестов. Не создавать дубликаты ради количества.

## Граница выпуска
Для READY_FOR_REVIEW нужны обозримый diff, выполненные применимые P0/P1 проверки, перечисленные оставшиеся P2/внешние BLOCKED, совместимость миграций и инструкция владельцу. Это не готовность всего объёма к production. Для заявления ALL_APPLICABLE_VERIFIED необходимы все применимые критерии нужного уровня. PRODUCTION_DEPLOYED не выставляется по этому заданию, поскольку выпуск не разрешён.

Откат к старому коду должен сохранять данные новых draft, outbox и обновлённые ограничения доступа; blind downgrade не является recovery plan. DB migrations additive, прежние миграции/allowlist не обходить. Разрушительные down/reset запрещены.

## Экономия контекста без снижения проверок
Начать с CORE_RULES, EXECUTION_PLAN и активного module-файла. Не читать одновременно FULL_PROMPT/ADMIN_SPEC/все modules. Сначала дешёвые targeted проверки, затем DB/browser и финальные guards для текущего diff. Не инвентаризировать повторно все 10k книг, изображения и старые отчёты при локальном исправлении callback. Не запускать content rebuild с сетевой записью до чтения scripts. При внешнем блокере продолжать независимые безопасные модули; фиксировать один checkpoint, не плодить R4/R5 документов вместо изменений.

Проверить ошибку membership, просроченный токен, отсутствие конфигурации, прямое обращение к action/API и повторное выполнение в другой вкладке. Сохранять CSP, origin/CSRF-защиту, no-store/noindex и совместимость текущего Cloudflare/OpenNext runtime; не переносить middleware в другой runtime без доказательства совместимости.

**Приёмка.** Тестовая матрица guest/reader/editor/admin/owner × MFA отсутствует/нужен/подтверждён/ошибка. Запрещённые запросы не читают закрытый контент и не меняют БД; обычный читатель не теряет разрешённое публичное чтение. Для production-политик без доступа статус не «проверено».

**Уточнение R2.** Разделить авторизацию Server Actions и обычных cookie-auth Route Handlers; защита последних подробно в M23. Запрет выдачи закрытых DTO действует и для prefetch/RSC, export, preview, recovery и command-search. 401, 403 и 503 не использовать взаимозаменяемо там, где это меняет безопасный retry/UI; скрывать существование недоступного объекта согласно текущей политике. Не приписывать ошибке assurance доказанный обход production: проверка и исправление должны быть подтверждены фактическими backend-тестами.

### Уточнение R3: auth callback, восстановление и приватный кеш
[R3E08, R3E09, R3E10] Callback использует собственный safeNextPath и объединение с настроенным adminSiteUrl. Из этого исходника не установлена эксплуатация open redirect. Требуется явный контракт допустимой продолженной навигации, нормализации и basePath, без исполнения произвольной цели, попадания code/token в итоговый URL и зависимости от недоверенного Host.

Восстановление собственного пароля использует provider session/updateUser и signOut. Не заменяй его requireStaff в начале: это способно заблокировать восстановление. Проверяй поддерживаемое провайдером подтверждение личности/recency и MFA-политику, не создавая новую кастомную auth систему; не расширяй полномочия на изменение другого аккаунта. Проверить одноразовость/истечение ссылки и понятный повтор после отказа, без реальных писем в тесте.

Закрытые DTO нельзя выдать до auth guard, рассчитывая только на общий layout. После logout/account switch/back-forward BFCache и восстановленная вкладка не должны открывать содержимое прежнего пользователя. Политика сохранности ввода не означает перенос частного draft между аккаунтами. Сохранять штатный серверный Auth/SSR refresh; не объявлять cookie HttpOnly обязательным без проверки требований используемой SSR-библиотеки. Подтвердить безопасность и успешную работу действительной конфигурации, не навешивать несовместимые флаги вслепую.

### M02. Ошибки данных без ложных нулей и потери формы — P0

**Основание.** safeCount возвращает count || 0 без учёта error. На ряде страниц отсутствующие data подставляются как пустые списки; при открытии статьи неуспешное чтение может прийти к notFound. [E04, E05]

**Реализация.** Общий тип результата загрузки должен различать успешные данные, подтверждённую пустоту, отказ, недоступность зависимости, повреждённый ответ и последнее достоверное, но устаревшее состояние. Не вводить null=0. В таблицах и KPI «0» допустим только после успешного запроса; иначе «Недоступно»/«Не проверено» с повтором и датой последнего успешного чтения, если она действительно известна.

Проверить dashboard, health, settings/team, articles/new/edit, translations, data-studio, library, dossiers, media, publication, history, analytics, SEO и все затронутые загрузчики. Не выводить «примените миграцию» при любом сетевом сбое. Код несовместимой схемы отличать от timeout, отсутствия прав и реальной пустоты. Сырые DB/provider errors — только в защищённый редактированный лог.

При недоступной EN-версии или другом обязательном компоненте bundle не открывать опасное сохранение, которое трактует недочитанные данные как пустые. Черновое пользовательское содержимое оставлять в форме; дать повторить чтение зависимости. Разрешать частичное сохранение только если серверный контракт явно защищает непереданные поля; иначе блокировать весь bundle с ясной причиной. Не очищать tags, category, media, EN и источники при их временной недоступности.

Разделить загрузку страницы и отправку формы. React error boundary не заменяет перехват ошибок server action/обработчика события. Ошибки транспорта после отправки показывать отдельно от подтверждённого отказа; повтор безопасен через идентификатор операции. Не ловить и не преобразовывать штатные redirect/notFound сигналы Next.js в обычные ошибки.

**Приёмка.** Инъекция сбоев каждого критичного запроса не даёт ложного нуля, пустого редактора или удаления. Ошибка чтения и неверные права не позволяют подтвердить существование чужой записи.

**Уточнение R2.** Успех частичной операции не равен успеху всей формы. Серверная запись могла состояться до неудачи уведомления, кеша или сохранения квитанции в браузере. Возвращать независимые сохранённую редакцию, состояние доставки, состояние резервной копии и доступность аудита. Retry принятой операции не должен заново пересоздавать сущность. Query-параметры ошибок/успехов не служат разрешением очистки, подтверждением commit либо основанием для удаления. GET/prefetch/предпросмотр не выполняют редакционные мутации.

### M03. Достоверные показатели и единый экран состояния — P1

**Основание.** Обзор содержит статические статусы и 12 отдельных подсчётов; настройки местами приравнивают наличие переменной к готовности. Health и Premium English используют разные проверки готовности перевода. [E04, E06, E07]

**Реализация.** Единый слой чтения эксплуатационных фактов для dashboard/settings/health/translations/publication. Разделить: configured, checkStatus, checkedAt, lastSuccessAt, evidenceVersion, reasonCode, permittedAction. Сохранить нынешние рабочие RPC и адаптировать их, не выполнять дорогие самотесты при каждом открытии страницы.

Проверка схемы должна отражать необходимые возможности. Не убирать текущие ограничения точной версии без анализа совместимости: capability checks должны сохранять запрет небезопасной записи при неподходящей схеме. Настройки отсутствуют — NOT_CONFIGURED; данные проверки недоступны — UNKNOWN; старый успех — STALE; реальная неудача — FAILED. Истечение срока не означает, что последний запуск завершился ошибкой.

Публикация оценивается по возрасту, ошибкам, последнему успеху и подтверждённой версии, а не только по размеру очереди. У backups и restore drill разные регламенты свежести, взятые из фактических расписаний. Допустимый интервал и grace period должны быть видимыми настройками/конфигурацией, не придуманными в интерфейсе.

Уточнить определения метрик: «Издания» не равны «Изданиям с валидным ISBN»; URL обложки не равен проверенной доступности и разрешению; статус published в БД не равен последнему опубликованному snapshot. Показывать знаменатель и область: все/отфильтрованные, RU/EN, диапазон, источник. Если число оценочное, так и подписывать.

Обзор владельца: блоки, требующие действия, последний завершённый выпуск, проблемы загрузки/перевода, черновики и проверки. Каждая проблема ведёт к соответствующему объекту с сохранённым фильтром. Не добавлять отвлекающие декоративные графики.

**Приёмка.** Одна и та же проверка даёт одинаковый смысл на всех экранах. Нет «Готово» по одному наличию env, нет искусственных успешных дат.

**Уточнение R2.** Schema health проверяет не только наличие функции/таблицы, но применимые возможности и реально включённые обязательные trigger/policy/grant contracts. Записанный migration SHA не доказывает отсутствие последующей ручной правки. Health read-only: не чинить schema, не запускать paid self-test и не изменять роли при простом открытии. Источник статуса и срок достоверности видны отдельно от отсутствия доступа к проверке. Не возвращать всем пользователям подробный приватный schema inventory.

### M04. Подтверждённая публикация, очередь и время — P1

**Основание.** public_build_outbox и экран requested/dispatched/deployed/failed уже есть. Досье, в отличие от статических материалов, доставляются через live no-store RPC и не требуют публичной сборки. Нельзя насильно переводить оба пути на одну технологию. [E08, E11]

**Реализация.** Общий UI состояния материала поверх двух адаптеров доставки: build-backed и live-backed. Различать сохранённый рабочий черновик, принятую к выпуску редакцию, ожидающую операцию и версию, доступность которой подтверждена по её реальному механизму. Git SHA недостаточен как идентификатор редакции контента.

Сопоставлять entityId + locale + revision/content fingerprint + operationId с release/snapshot manifest и успешным deployment. Один build может включать много изменений; поздний сигнал от старого build не должен отмечать новые редакции опубликованными. Проверку live-досье связывать с опубликованной редакцией/variant bank, а не с запуском Pages. В UI явно различать подтверждение доставки артефакта и отдельный live smoke на пользовательском адресе.

Сначала проверить существующие coalesce/head-check/экспортёры. При выпуске контента событие outbox и изменение публикуемой записи должны быть в одной транзакции там, где этого ещё нет. Черновик не создаёт публичный выпуск. Ошибка отправки внешнему deploy-провайдеру оставляет сохранённое событие для повтора. Сбой ответа после commit не должен создавать новую редакцию при повторе той же операции.

Идемпотентность, ограниченные повторы, backoff, защита claim/lease в транзакционном хранилище; не использовать KV как lock. Не обещать exactly-once внешней сети. Повтор для активной операции не порождает дубликаты; зависшую отличать по lease/heartbeat. Сборки объединять с учётом версии, а не терять промежуточные запросы. Не уничтожать историю outbox при очистке UI.

Добавить возраст очереди, последнее подтверждение, понятное имя материала, публичный адрес, ссылку на сборку и безопасный повтор конкретной ошибки. Ограничить статусный polling видимой вкладкой и активными задачами.

Время хранить в UTC; ввод и отображение используют явную IANA-зону. Сохранить существующую редакционную зону; при её отсутствии выбрать документированное значение Europe/Moscow с возможностью изменить до планирования. Зону браузера не применять молча. При вводе показывать дату, время, зону и UTC; отдельно обрабатывать неоднозначное/несуществующее местное время при смене DST. Date-only событие не преобразовывать в выдуманное время. Не менять уже запланированные instants. Интервал планировщика не выдавать за гарантию секунды публикации.

**Приёмка.** Тесты commit-then-timeout, двух вкладок, повторного webhook, старого build, нескольких изменений в одном build и независимой live-доставки досье; ни один успешный тост не утверждает непроверенную публичную версию.

**Уточнение R2 — обязательное сохранение действующих гарантий.** Повторный разбор SQL подтвердил транзакционные outbox-триггеры на 20 таблицах; обычный action не обязан создавать вторую транзакционную очередь. Отдельный trigger-event и explicit request-event намеренно могут сосуществовать. Нельзя deduplicate все pending строки по entityId, переиспользовать старый outbox ID или помечать новой редакции статус старого build. Отличать повтор одного пользовательского operationId от разных добросовестных событий. UI может группировать их без потери идентичности. Проверить сохранность при delayed commit и high-water mark экспорта, а также неизвестный результат mark_public_build_dispatched. [R2E16, R2E17]

Существующий экспорт уже повторяет обычный и Premium-снимок совместно и не публикует промежуточный hash. Сохранить это поведение и испытать, а не переписать exporter. Под «черновик не публикуется» понимается неизменность публичной редакции/публичного snapshot; допустимое внутреннее invalidation-событие для актуализации зависимостей само по себе не является утечкой. Не отключать durable triggers ради пустого outbox в тесте. Очереди рабочих autosave не должны автоматически выпускать контент. [R2E18]

### Уточнение R3: намерение повтора и валидный ID
[R3E04, R3E05] retryPublicationAction читает status, но сам не ограничивает deployed-состояние; UI-фильтр не является серверным контрактом. Разделить retry того же намерения и новый осознанный rebuild. Проверить терминальное/активное состояние и гонку между чтением и новой командой в устойчивой границе, сохраняя append-only outbox. Не удалять добросовестные row-trigger и explicit события ради требования «один повтор».

У любой межслойной команды ID должен быть проверен до следующего RPC: scalar UUID, объект результата, outbox bigint и revision token — не взаимозаменяемы. Нельзя допускать undefined ID и затем уходить в legacy queue как будто современной функции нет. Подтверждённая несовместимость сигнатуры, неверный DTO и временный сбой должны быть различимы от действительно неустановленной capability. Существующий fallback сохранять только в его доказанных границах совместимости, не выключать текущую защиту и не раздавать service-role.

Ошибку дополнительного audit/mark-dispatched после известного внешнего успеха не исправлять повторным вызовом провайдера. Показывать точный известный результат и необходимость reconciliation; реальная мутация и существующий trigger-event не должны исчезнуть из истории.

### M05. Редактор статей и защита рабочих черновиков — P0/P1

**Реализация.** Сначала исследовать существующие ArticleEditor, working-draft actions, atomic bundle, autosave/recovery и preview. Не вводить второй черновик с конфликтующей семантикой.

Разделить действия «Сохранить черновик», «Передать на проверку», «Запланировать», «Выпустить». Не менять опубликованную редакцию обычным автосохранением. В закреплённой панели показывать dirty/saving/saved/offline/conflict/unknown-outcome с временем именно подтверждённого сохранения. После ошибки сохранять ввод, курсор, выбранный язык и доступный контекст формы.

Оптимистическая конкуренция: хранить серверный revision/token точности без потерь; не сериализовать timestamp с потерей микросекунд. Проверять ожидаемую версию в транзакции; не реализовывать read-then-write без условия. При конфликте — сравнение с серверной версией и сохранение своей копии, а не автоматический last-write-wins. Поздний ответ старого автосохранения не сбрасывает более новые локальные изменения.

Обработать уход через sidebar, Ctrl+K, внутренние ссылки, back, закрытие/перезагрузку и истечение сессии. beforeunload — только дополнительная защита, не механизм сохранения. При повторной авторизации не включать черновик в URL и не открывать его другому пользователю. Использовать существующее защищённое серверное восстановление. Постоянное локальное хранение неопубликованного текста не добавлять без отдельной политики; если оно уже есть, проверить scope пользователя/материала, срок и очистку на logout.

Предпросмотр показывает выбранный черновик, язык и режим экрана; не публикует его, не индексируется и не раскрывает его через публичный URL. Проверить изображения, списки, таблицы, сноски/библиографию и длинные материалы. Ошибки полей связать с конкретным контролом и общей сводкой. Ссылки и HTML проходят существующую безопасную обработку; её нельзя отключать ради точного восстановления опасной разметки.

**Приёмка.** Повторное сохранение не вводит новых преобразований содержимого; сохранение при сетевой ошибке/конфликте не уничтожает текст. Исключённое baseline-поведение из ограничений не исправляется. Действия с черновиком не запускают публичный выпуск.

**Уточнение R2.** Общие изменения редактора проверять вместе с M19/M20: новый clean/saved сигнал относится к принятой версии, не к нажатию кнопки. Истёкшая auth-сессия должна приостанавливать запись, не уводя пользователя без защищённого восстановления и не копируя весь текст в callback URL. Применение или удаление editor-template не может заменить тело существующей статьи без соответствующего явного действия; права personal/shared в M24.

### Уточнение R3: достоверный предпросмотр, а не похожая карточка
[R3E06] В просмотренной article preview загрузка/рендер обложки опираются на cover_external_url; cover_media_id в исходной проекции не выбран. Проверить managed-cover сценарий и вынести минимальный общий resolver URL/alt/focus/приоритета, совпадающий с public renderer. Не импортировать всю Vite/3D-публичную часть в admin Worker ради повторного использования одной функции.

Выбор preview должен иметь точную идентичность: entity, locale, origin(local/autosave/working draft/published), revision/fingerprint. По умолчанию показывать, что именно просмотрено. Не выдавать сохранённый B за несохранённый C, не привязывать review новой редакции к старому preview. Безопасный локальный preview допустим, если он явно обозначен и не создаёт публичную публикацию; не записывать его скрыто ради просмотра.

RU/EN, внешняя/managed обложка, галерея, таблица и библиография должны пройти сравнение на фиксированных viewport. Узкая рамка вокруг desktop CSS недостаточна, если реальные responsive правила продолжают видеть широкий viewport. Выбери лёгкую изолированную страницу/iframe/доказанный эквивалент, совместимый с CSP/X-Frame-Options и нужным origin, не ослабляя глобальную защиту ради iframe. Отсутствующий EN и ошибка его чтения различаются.

Для небезопасного legacy HTML проверять безопасную проекцию и существующие sanitization/URL contracts, а не разрешать активный контент ради визуального совпадения. Исходный контент не массово ремонтируется.

### M06. История, сравнение и безопасное восстановление — P1

**Основание.** Текущий общий restoreRevisionAction обновляет целевую запись, отдельно пишет аудит и запрашивает public build; для основного издания есть многошаговая компенсация. UI предлагает немедленную публикацию восстановленной версии. [E09]

**Реализация.** Сравнение текущей сохранённой, рабочей и исторической версии: поля, RU/EN, контент, медиа, ссылки, метаданные. Сравнение read-only и без повторного сохранения статьи. Для длинных HTML использовать ограниченный безопасный diff без выполнения скриптов; не выводить полный мегабайтный snapshot в каждом ряду списка.

По умолчанию «Восстановить в черновик» для сущностей с существующей черновой моделью. У статьи восстановление использует рабочий черновик, а не опубликованную articles-запись. Если черновик уже есть, предложить сравнить/сохранить его отдельно; не уничтожать его молча. Приёмка: значение публичной редакции не изменилось до отдельного выпуска; внутренние технические invalidation-события оцениваются по контракту M04, а не запрещаются целиком.

Не приклеивать к старому немедленному action новое название. Для сущностей без черновой модели показать реальное последствие и безопасный preview; создать специализированный непубличный restore proposal только при необходимости, не общий дублирующий CMS. Немедленный откат — отдельное действие с достаточной ролью, причиной, ожидаемой версией и явным подтверждением.

Использовать проверенные специализированные RPC/инварианты обычного сохранения; восстановление не должно обходить RU/EN bundle, права, primary edition и ограничения Site Studio. Многозаписные изменения, аудит и outbox сделать атомарными в БД, где этого ещё нет. Не рассчитывать на компенсацию после обрыва процесса как на эквивалент транзакции.

Не восстанавливать владельца, привилегии, deleted_at, серверные поля и одобрения из произвольного snapshot. Для новой редакции повторно оценить нужные проверки; журнал append-only. Показывать понятного исполнителя, причину операции, истинную причину недоступности восстановления. Не выдавать любую нересторируемую запись за «Объект удалён».

**Приёмка.** Старую версию можно изучить без записи, восстановить безопасно, отменить proposal и выпустить отдельно; при сбое транзакции нет частичного отката связанных сущностей.

**Уточнение R2.** Контракт восстановления не должен требовать отсутствия любых технических outbox строк: обязательна неизменность опубликованной редакции и отсутствие несанкционированного выпуска. Для действий с каскадными зависимостями использовать M21/M22. Дифф показывает пропущенные запрещённые поля и причины, не восстанавливает одобрения по одному клиентскому JSON. Snapshot с неизвестной будущей схемой не загружается как пустой объект; unsupported и corrupt различаются.

### M07. Переводы RU/EN и управляемая очередь — P1

**Основание.** Premium English уже имеет provider self-test, очередь/статусы операций и сохранение ручного EN. Эти механизмы нужно развить, а не заменить. [E07]

**Реализация.** Отдельно показывать происхождение текста, редакционное качество, соответствие текущему RU и состояние технической задачи. Успешный ответ модели не означает человеческую проверку или опубликованную версию. У ручного перевода — явная защита, сохраняемая также при retry, backfill, restore, import и изменении русского источника.

Связать машинную задачу с entity/locale, fingerprint исходника, конфигурацией и версией. Если RU изменился до завершения, не записывать результат поверх нового состояния: пометить устаревшим и дать создать новую задачу. Ручной EN не пересоздавать и не удалять; предупредить, что русский оригинал изменился. В панели — просмотр RU и EN рядом, источник, дата и статус проверки.

Расширить существующую очередь: pending/running/retry/failed/cancelled/completed с понятными действиями, количеством обработанных/пропущенных/ошибочных, cursor и причиной пропуска. Повторять только неуспешные/устаревшие элементы по правилам, не гонять заново весь корпус. Уважать kill switch, concurrency, лимиты и резерв ручных версий. Stop не прерывает транзакцию произвольно, а останавливает выдачу новых задач и безопасно фиксирует текущую.

Не выполнять долгий пакет в одном HTTP-запросе Worker. Переиспользовать имеющегося durable/job-обработчика; минимальная новая очередь допустима лишь при доказанном отсутствии нужного механизма. Не менять провайдер, модели и платный fallback. В разработке и CI использовать контролируемый mock провайдера; реальный self-test только в явно разрешённой изолированной среде, с понятным учётом затрат и без полного текста в логах.

Health должен читать тот же актуальный результат self-test, что и страница переводов; проверка старой модели не подтверждает новую конфигурацию. В описание интерфейса подставлять фактическую конфигурацию, а не фиксированное рекламное название модели.

**Приёмка.** Ручной EN не меняется ни одним автоматическим маршрутом; поздний ответ не записывает устаревший перевод; отменённая или заблокированная задача не выглядит выполненной.

**Уточнение R2.** Покрыть путь site-copy, где вызов переводчика сейчас расположен до сохранения. Внешний успешный ответ не должен теряться при последующем локальном конфликте без понятного результата; не возобновлять работу на устаревшем sourceHash и не создавать расходы повтором всех завершённых сегментов. Контент источников и ответов модели — недоверенные данные, не инструкции для запуска инструментов или изменения правил публикации. Подробная интеграция site-copy в M24.

### Уточнение R3: свежесть, попытки и семантика продолжения
[R3E01, R3E02, R3E03] В translatePremiumArticleBatchAction published EN пропускается как current до ensurePublishedArticlePremiumEnglish. Между тем helper умеет вычислять source hash и учитывать machine ownership. Нельзя считать published доказательством свежести. Сначала использовать безопасную проверку source revision/hash + ownership; общий helper переиспользовать или разделить на чистый классификатор и дорогую операцию без дублирования. Не запускать модель только ради определения актуальности. Поля «машинный/ручной», «актуальный/устаревший/неизвестно» и «опубликован/черновик» — отдельные оси.

MAX_ARTICLE_TRANSLATIONS сейчас ограничивает translated, а conflict не увеличивает его. Поэтому серия конфликтов способна продолжать дорогие попытки до scan limit. Ограничь independently scanned candidates, expensive attempts, provider calls двух проходов, retries и elapsed/deadline. Использовать измеримые текущие budgets, не увеличивать их ради теста; при отсутствии лимита задать обоснованный локальный default и документировать. Отмена/timeout не гарантируют отмену уже принятого внешнего запроса — не объявлять его несуществующим и не делать слепой дубликат.

Проверить ordering updated_at + OFFSET и равные даты при изменяющемся наборе. Выбрать минимальную устойчивую стратегию: стабильный tie-breaker и snapshot/keyset/фиксированный bounded набор с чётким resume-протоколом; не переписывать все каталоги админки в keyset. Устаревший cursor не должен давать ложный полный прогресс. Уже сделанные и ручные переводы не отправляются заново ради статистики.

SQL runtime явно различает активный staff-bounded-sync-resume и service-role-only lease API. Сохранить это разграничение. Не обещать фоновую очередь, если команда продолжает синхронный скан. «Продолжить оставшиеся» и «Повторить неудавшиеся» — разные намерения; UI должен показывать фактический эффект. Потерю журнала после частичного success восстанавливать по существующим данным/квитанциям, не повторной генерацией всех элементов.

Техническое machine completion не становится личной редакторской проверкой. Поведение существующих опубликованных записей не менять массово; новые контрактные исправления проверять на fixtures, ручной EN сохранять.

### M08. Каталог книг, поиск, издания и импорт — P1

**Основание.** Пагинация, фильтры и раздельные произведения/издания существуют. Основной запрос каталога фильтрует title; ссылки из Data Studio и workspace-контекст необходимо проверить сквозным сценарием, а не объявлять сломанными по фрагменту файла. [E10]

**Реализация.** Поиск по русскому, оригинальному и альтернативному названию, автору/псевдониму, legacy/canonical ID и ISBN издания. Точные ISBN/ID и совпадения названия имеют объяснимый приоритет. Нормализация только поискового ключа, без записи в авторский текст. Защитить параметры RPC/SQL/PostgREST, ограничить длину и число результатов. Проверить буквальные %, _, кавычки и пустой ввод. Не строить SQL или or-фильтр из необработанной строки.

Сохранить серверную пагинацию, стабильную сортировку с уникальным tie-breaker, фильтры и контекст после редактирования. Не загружать весь книжный архив в браузер. Отдельный picker изданий ищет по всему разрешённому каталогу, а не только по активному фильтру списка. Не объединять произведение, перевод и издание. Отсутствие ISBN у старого издания не делает произведение неверным; валидный ISBN не является доказательством всех сведений.

Карточка произведения объединяет навигацию к RU/EN, источникам, фактам, изданиям, визуальным материалам, досье, связанным статьям, редакционному решению и публичной версии. Показывать причины неготовности отдельно; не вычислять «качество 100%» из заполненности полей.

Довести существующий импорт: кандидаты, сравнение с возможными совпадениями, отклонение с причиной, откладывание, dry-run подтверждённого пакета и понятный итог. Подтверждение кандидата не означает автоматическое одобрение всех фактов/прав. Идемпотентность provider + external_id/стабильного ключа, понятная диагностика конфликтов, сохранение происхождения. Не сливать записи автоматически по похожему названию, не удалять сомнительные дубли и не перезаписывать ручные descriptions/EN/источники.

Для массовой операции — ограниченный размер пачки, checkpoint, результат по каждой записи и повтор только failed. Уникальное основное издание и ссылочная целостность обеспечиваются транзакцией/ограничениями БД, включая повторные запросы и восстановление. Не создавать вторую базу стран/авторов.

**Приёмка.** Поиск по оригинальному названию и ISBN ведёт к правильной сущности; записи за пределами первой страницы доступны; повтор импорта не создаёт копий и не меняет ручные материалы. Нагрузочные fixtures около 10 000 записей, не выдуманный production count.

**Уточнение R2.** Импорт имеет идентичность пакета/версии и строки, dry-run не пишет; повтор того же пакета даёт понятный unchanged/duplicate/conflict, а не новое произведение. Связи writer/work/edition выбираются по постоянным IDs, не по совпавшему имени. Обработать потерю соединения и изменённый вручную объект между preview и apply. Применять пачки по управляемому лимиту с cursor/receipt и отчётом по каждой строке; не обещать одну транзакцию всего большого архива через браузер. Дополнительные скачивания и источники не запускаются при простом открытии каталога. Неподдерживаемый формат не преобразуется молча.

### M09. Досье: полный каталог и формы без обязательного JSON — P1

**Основание.** Список показывает последние 50 досье без полного поиска/пагинации. BookDossierEditor содержит поле raw JSON для структуры, источников и прав; dirty нового draft без record нуждается в отдельной проверке. Сохранение, review и публикация уже имеют собственный workflow и revision. [E11, E12]

**Реализация.** Полный серверный каталог с поиском, страницами, языком, статусом и связью с произведением. Переход из книги сразу выбирает её досье; новый документ создаётся через безопасный picker канонического произведения, не требует знания составного ключа. Не вводить новое общее хранилище досье.

Формы для разделов, блоков, элементов, источников, source IDs, оснований прав и уровня спойлеров. Выбор связанной записи вместо ручного ввода технического ID. Удаление источника/основания показывает зависимые элементы и не оставляет висячих ссылок. Обязательные разделы добавляются идемпотентно; переупорядочивание не пересоздаёт их стабильные ID. Сохранить V2, существующие типы, validators и review pipeline, а не менять формат ради формы.

Экспертный JSON оставить дополнительным способом редактирования с проверкой, preview изменений и явным применением. Неприменённый raw-текст не должен теряться при изменении формы. Ошибка JSON не подставляет пустой документ. Семантически одинаковый JSON не должен создавать ложную содержательную правку, но ввод нельзя переформатировать до применения.

Отслеживать dirty от исходного пустого/сохранённого baseline даже у нового досье. Защитить уход и действие при ожидающем запросе. Перехватывать сетевые ошибки и неожиданные ответы action/измерителя макета; не сбрасывать введённый текст. Все поля, влияющие на отправляемую редакцию, либо блокировать на время операции, либо обрабатывать версионно; старый ответ не затирает новые изменения.

Каждое содержательное изменение сбрасывает необходимые подтверждения и proof по правилам текущей схемы. Не выставлять галочку личной проверки программно. ReviewedBy/reviewedAt определяются сервером. Доказательство макета привязано к версии содержимого и конфигурации; raw-edit также делает его неактуальным. Ошибка измерения не является одобрением. Live-доставка использует действующий variant bank и настройки спойлеров, не публичный экспорт черновика.

Коды ошибок перевести в пояснения и привязать к полям, сохранив технический код в деталях. Причины архивации/отзыва и история остаются обязательными.

**Приёмка.** Обычное досье можно подготовить без JSON; источники/права не получают ложного одобрения; можно найти старую запись; новая несохранённая форма и старые ответы не теряют ввод.

**Уточнение R2.** В SQL уже действуют шесть последовательных человеческих одобрений, проверки checksum, прав, design proof и публичной проекции. Полные тексты, цитаты, media-блоки и articleReuse заблокированы; для articleReuse отсутствует необходимое source-block approval. Не открывать эти возможности для удобства формы и не подставлять фиктивное разрешение. Ссылка на уже опубликованную авторскую статью не равна переиспользованию её текста. Preview/design proof не выдаётся за фактический DOM/3D browser test, если измерен только canvas. Истечение прав/отзыв, spoiler-mode и срок допустимой public-проекции проверить в реальном RPC. Сырой draft/банк всех вариантов не отправлять читателю. [R2E19]

### M10. Завершённый редакционный цикл литературных новостей — P1

**Основание.** /literary-news читает приватную held-очередь из KV и направляет подтверждённые материалы в data/news/reviewed.json через GitHub. Сама эта страница не завершает редакционный цикл. Сборщик и парсеры уже существуют. [E13]

**Архитектура.** Сначала проверить, не внедрена ли более новая реализация новостей в рабочей ветке. При её отсутствии предпочтительно хранить редактируемые карточки и review в существующем Supabase; опубликованный read model/snapshot выдавать через текущий публичный конвейер. KV оставить снимком discovery/состояния источников, не использовать для конкурентных черновиков и lock. Не делать одновременные самостоятельные записи подтверждённой новости и в JSON, и в БД.

Оформить короткий ADR единственного источника истины. Старый reviewed.json — только проверяемый вход миграции или генерируемый snapshot, а не вторая редакционная система. Импорт существующих подтверждений должен сохранять provenance/ID и не приписывать человеку новое одобрение. Dry-run сверяет количество, идентичность, даты и хеши; переключение production в эту подготовку не выполнять. Если действующая архитектура обоснованно требует Git-backed-публикации, допускается один защищённый PR-путь из UI вместо DB-authoring, но с теми же версиями и без расширения секретов; документировать выбор и не оставлять два master-хранилища.

**Редактор.** Source URL и источник, заголовки RU/EN, собственные краткие описания, категория, связанные книга/автор/страна, дата публикации источника, дата обнаружения и отдельно дата/диапазон события с точностью. Не выдумывать время неизвестной даты. По правилам текущего публичного schema отсутствие обязательных сведений блокирует выпуск с понятной причиной. Предпросмотр обеих языковых версий и видимости источника.

**Workflow.** Найдено/held → редакционный draft → review → approved → scheduled/published; rejected/withdrawn/correction по действующим или обратно совместимым статусам. Это семантические состояния, не приказ заменить все существующие enum. Проверка относится к конкретной версии. Редактор готовит материал, уполномоченный сотрудник подтверждает согласно матрице прав. Исправление опубликованного материала создаёт редакцию; отзыв имеет причину и подтверждается публичной доставкой.

Повторный сбор не восстанавливает отклонённую карточку и не перезаписывает ручной текст. Discovery ID, normalized source URL и event grouping используются для кандидатов на дубли, не для бесконтрольного слияния разных событий. Нужны отложить, отклонить с причиной, вернуть в работу, фильтры, история и безопасные групповые действия без массового автоодобрения.

Внешние фиды/тексты считать недоверенными данными, не инструкциями. Безопасные URL, ограниченные размеры, timeout, проверка redirects и защита от SSRF для серверного чтения. Не передавать credentials внешним сайтам. Публичная доступность источника не подтверждает факты или права на его текст/изображение. Не добавлять в этот этап сотни новых источников вместо завершения редактора.

**Приёмка.** Новость можно обработать, исправить и отозвать из UI без ручного JSON/Git; неподтверждённые карточки не попадают на публичный сайт; повтор сборщика не уничтожает редакционное решение.

**Уточнение R2.** Назначение — существующая «Литературная повестка». Не добавлять новостные статьи и самостоятельные публичные страницы вместо её карточек. Утверждённая новость, событие календаря и источник имеют разные идентичности и даты. До перехода на новый master сверить именно действующую реализацию: не отменять локальные R8/R9/R10 или более новые работы, если они уже реализуют workflow. Специальные контракты календаря и внешней доставки в M25. Отдельное увеличение числа источников/готовых карточек не считается результатом этого инфраструктурного задания.

### M11. Медиатека, обложки и безопасные массовые операции — P1

**Основание.** Media Studio уже содержит корзину, связи, восстановление, замену, права и batch upload. Нельзя объявлять их отсутствующими. Полноту ссылок для всех способов хранения нужно проверять. [E14]

**Реализация.** Составить карту media references: RU/EN article content, cover/OG, рабочие черновики, revisions/autosave, pages, homepage, banners, categories, books/editions, artworks/dossiers и статические справочники — по фактическим адаптерам. Различать current usage и historical usage. Внешний URL и Storage asset не всегда одна сущность. Не выполнять очистку на основании неполного графа; при недоступной проверке запретить purge и показать причину.

Замена: preview всех текущих затрагиваемых полей, версии исходного/нового файла, контрольные суммы и конфликт при конкурентной правке. Исторические ссылки сохраняются и позволяют восстановление. Не перезаписывать объект Storage по старому ключу с разрушением истории; применять существующую версионную модель. Новый источник/права не наследуют «подтверждено» без проверки. Окончательное удаление только по существующим строгим правам, отдельному подтверждению, retention и повторной проверке графа в момент действия; production purge не запускать.

Batch upload: сохранить нынешние размерные/форматные ограничения до измерений; результат по каждому файлу, preview общих/индивидуальных метаданных, прогресс, повтор failed без повторной загрузки успешных. Не присваивать одной массовой галочкой проверенные права разным картинкам. Ошибка одного файла не должна скрывать уже сохранённые. Повтор по тому же operation/file fingerprint идемпотентен в рамках допустимой модели, не сливает автоматически разные лицензии одинаковой картинки.

Оценить ненужные public builds: загрузка неиспользуемого файла не должна требовать много полных сборок, если публичный контракт этого не требует. Использовать существующее объединение событий для пачки. Не перестраивать транспорт на прямые uploads и не повышать body limit без доказательства необходимости и проверки прав/подписанных URL.

Добавить фильтруемую очередь качества обложек: нет изображения; недоступность последней проверки; несоответствие выбранному изданию, отмеченное редактором; недостаточное разрешение по типу использования; незаполненное происхождение. Доступность проверять ограниченной задачей, не массовым fetch на каждое открытие страницы. Автоматическая проверка URL не подтверждает право использования или идентичность издания. Не скачивать и не генерировать обложки в рамках этого задания.

**Приёмка.** Ни текущая статья, ни её восстанавливаемая версия не теряют изображения; повтор batch не плодит успешные uploads; отсутствие полного графа исключает разрушительные действия.

**Уточнение R2.** Не смешивать public URL и подтверждённое публичное использование в материале; статус draft статьи не закрывает доступ к публичному файлу. При изменении media identity сбрасывать только привязанные к прежнему файлу подтверждения, не переносить автоматически прежнюю лицензию на новые байты. Удаление учитывает активные draft, revision, recovery и публикационные операции; невозможность прочитать граф зависимостей закрывает purge. Границы upload и crash recovery подробно в M23.

### Уточнение R3: окно вставки — отдельная поверхность медиатеки
[R3E07] /api/media/assets возвращает максимум 60 активных записей и ищет только alt_text. EditorMediaDialog не передаёт page/cursor и не имеет навигации результатов; body.assets неверной формы заменяется пустым массивом. Успешная пагинация /media не закрывает эти проблемы.

Сделай bounded пагинацию/infinite-loading внутри существующего диалога с устойчивым created_at + id порядком. Выбор способа счётчика total/hasMore не должен вынуждать тяжёлый exact count на каждую букву. Поиск по original_name, alt/caption/collection должен быть явным и безопасным, существующее экранирование %, _, backslash сохраняется. Не вводить второй полнотекстовый сервис.

GET response имеет проверяемый envelope и минимальный валидный asset DTO. Malformed HTTP 200 — ошибка зависимости, не empty state. Не передавать лишние сведения о закрытых объектах, signed URL не логировать. Предусмотреть refresh после подтверждённой upload, защиту от позднего ответа старого запроса и очищение/изоляцию списка при смене аккаунта.

Доступность выбранного asset подтверждается при сохранении ссылки, а не доверяется старой карточке. Если файл отправлен в корзину/заменён, исходный текст формы остаётся у редактора; не вставлять новый произвольный файл вместо него. Переиспользовать существующий useEditorDialogFocus — не создавать второй конфликтующий focus trap.

Боковая навигация на телефоне доступна, не заслоняет форму; широкие таблицы имеют управляемую область прокрутки/адаптивный список. Контраст и фокус используют текущие токены, не новый брендинг. Проверки 400%/320 CSS px допускают осознанно горизонтально прокручиваемую таблицу внутри контейнера, но не весь документ и не недоступные кнопки.

### M13. SEO: полный список проблем по фактическому результату — P2

**Основание.** SEO-страница имеет редиректы и preview 12 статей с пустыми полями. Это проверка полей CMS, а не полная проверка опубликованного HTML. [E16]

**Реализация.** Переиспользовать scripts/audit-seo-release.mjs, audit-public-routes и прочие действующие проверки. Привести результаты к read-only отчёту с entity/path/locale, кодом проблемы, серьёзностью, проверенным release/snapshot, временем и ссылкой на редактор. Полный список с фильтрами/пагинацией; после исправления замечание закрывается только по новой проверке нужной версии, не по нажатию «Сохранить».

Различать raw CMS override и вычисленное значение. Пустой canonical_url не является автоматически отсутствующим canonical на публичной странице, если публичный renderer законно рассчитывает его. Предпросмотр обязан использовать тот же resolver, что и сайт. Проверять итоговые canonical, индексируемость, title/description/OG, sitemap, hreflang/языковые связи и JSON-LD по тем типам страниц, которые реально существуют.

Проверять циклы и цепочки редиректов, self-redirect, внутренние назначения и конфликты со старыми Tilda routes. Не менять slug/URL, robots, noindex или canonical массово без preview и отдельного редакционного решения. Не создавать новые публичные страницы из одной кнопки аудита.

Загрузка отчёта не запускает большой сканер синхронно в Worker. Хранить ограниченные данные/артефакт проверки с версией. Ошибка сканера или устаревший отчёт видимы. Исправления метаданных не переписывают статью и ручной перевод. Не генерировать «SEO-текст» автоматически и не обещать позиции поисковой выдачи.

**Приёмка.** Любое замечание можно найти и открыть; поля с корректным публичным fallback не получают ложную ошибку; старый зелёный отчёт не подтверждает новую сборку.

**Уточнение R2.** Смена taxonomy/page slug проверяется как связанное изменение URL, не только заполненность поля. Redirect-loop/цепочки/конфликт с существующим маршрутом должны блокироваться до выпуска; временные redirects и действительно внешние canonical не нормализуются автоматически по общей маске. Read-only HTTP-проверка URL подчиняется ограничению адресов/редиректов/таймаутов и не становится SSRF-прокси для произвольных введённых ссылок. Не скачивать весь интернет или платные отчёты ради SEO-панели.

### Уточнение R3: несовпадение RPC-результата и существующие SQL guards
[R3E11] create_seo_redirect_guarded в просмотренной SQL-миграции возвращает uuid. createRedirectAction передаёт `data.id` в requestRedirectBuild. При scalar UUID это undefined. Подтвердить фактическую сигнатуру на тестовой effective schema, воспроизвести полную цепочку создания и передать правильный валидированный ID. Предпочтителен минимальный адаптер вызывающего кода; не менять SQL на JSON-объект без анализа всех callers и совместимости.

Не путать этот дефект явного запроса публикации с потерей самого редиректа: штатные row-trigger/outbox могут сохранить underlying mutation. Ошибка уведомления/fast dispatch и существование canonical записи показываются отдельно. Обязателен DB integration test фактического возвращаемого значения, а не mock `{id: ...}`, который скрывает ошибку.

У redirect уже есть guarded RPC с advisory lock, CAS, проверками коллизий и транзакционным audit. Сохранять их. Проверить полноту сравнения эквивалентных внутренних адресов (same-origin absolute/root-relative), canonical fallback фактического renderer и legacy маршруты. Не удалять старые редиректы, не вводить blanket-normalization всех URL; публичная карта адресов и разрешённые external destinations сохраняются.

### M17. Эксплуатация, резервные копии и производительность — P1/P2

**Основание.** Конфигурация выпуска использует private catalogs и проверку SHA; health имеет markers backup/restore. Текущие реальные backup и соответствие production в этой подготовке не проверены. [E06, E20]

**Реализация.** Показать версии admin build, публичного release, схемы и private catalogs как разные значения. Проверка доступности и соответствия checksum, последний успех и причина несовпадения; не выводить секреты/внутренние access URLs. Механизм публикации каталогов не должен обещать транзакционность нескольких KV-ключей: версионированные blobs, manifest и переключение указателя с терпимостью к eventual consistency либо существующий эквивалент. При несовпадении — запрет опасной операции и ясное состояние, не автоматическая публикация неизвестного каталога.

Backup/restore: проверить действующие jobs и evidence markers. «Есть marker» не доказывает полноту копии. Отчёт должен различать DB, Storage и конфигурацию, возраст, последний результат и отдельную проверку восстановления в изолированной среде. Не экспортировать production-дамп в PR; не выполнять restore на production. Выяснить текущие расписания, retention и цели восстановления, не придумывать успешно проверенные RPO/RTO.

Производительность: сначала baseline на фиксированных fixtures, затем targeted profile. Измерять число запросов, объём данных, cold/warm выдачу, открытие большой статьи, ввод, поиск и worker size. Рассмотреть агрегированную сводку вместо 12 count-запросов только при пользе; RLS/ошибки/семантика подсчётов сохраняются. Для длинных историй не читать полный snapshot каждой строки; для каталога не делать N+1 и client-side загрузку всего архива.

Индексы добавлять по реальным predicates и EXPLAIN в изолированной БД, без ANALYZE тяжёлых запросов на production. Не использовать кеш авторизации между запросами; health/report cache отдельно, ограниченный и помеченный датой. Таймауты и лимиты сетевых запросов, небольшие пакеты фоновых операций, прекращение polling скрытой вкладки. Не поднимать лимиты Worker вместо устранения измеренного источника нагрузки.

Проектный benchmark: одинаковое окружение, фиксированные наборы около 10 000 записей и длинный документ, не менее 20 повторов для сравнения warm-операций; отдельно отмечать cold. Не объявлять процентили по 2–3 запросам. Регрессию более 15% исследовать с учётом шума, а не скрывать обновлением baseline. Соблюдать существующие строгие performance/worker size gates, не ослаблять их ради этого относительного критерия.

**Приёмка.** Измерения до/после воспроизводимы; опасные действия закрыты при неполных каталогах; статус восстановления подтверждается отдельным изолированным испытанием или честно отмечен BLOCKED.

**Уточнение R2.** Отдельно проверять схему, приватные KV-каталоги, content snapshot, admin Worker и public release. Зелёный build по Git SHA не доказывает актуальность каталога или редакции базы. Backup marker означает зарегистрированный запуск, не доказанное восстановление: для restore drill нужны фактический результат, объём, покрытые DB/Storage refs и безопасная изоляция. Не запускать drill на production и не удалять старые данные по одному истёкшему UI TTL. Хранение диагностик/receipt должно сохранять сведения об активных и неизвестно завершившихся операциях.

### M19. Страницы: согласованность HTML/JSON и рабочая редакция — P0/P1

**Основание.** В просмотренном `createPageAction` непустой текст переводится в `content_html`, а `content_json` записывается пустым документом. `PageEditor` предпочитает `page.content_json || page.content_html`. Пустой объект документа является truthy: первоначальное содержимое редактора может не соответствовать сохранённому HTML. Это вывод из двух исходников, а не подтверждение потери конкретной production-страницы. Проверка media identity не заменяет проверку содержимого документа. [R2E01]

**Сделать.** Выделить единый контракт загрузки и сохранения страницы на основе уже используемых TipTap extensions, санитизации, медиа-идентификаторов и модели версий. Сам факт наличия объекта не определяет, какая редакция правильная.

Для новой страницы из простого текста строить согласованные JSON и HTML до первой записи. Безопасно обрабатывать угловые скобки и текст, который не заявлен как HTML; не интерпретировать пользовательский plain text как произвольную разметку. Для legacy-страницы с непустым HTML и пустым JSON показать явный режим совместимости/предпросмотр, построенный существующим безопасным парсером. Загрузка не должна молча переписывать БД. Перед переходом к новому представлению сохранить исходный снимок и показать содержательную разницу. Если оба представления непустые и расходятся, не угадывать правильное по длине или времени клиента: показать конфликт и сохранить оба до решения.

Проверять текстовые блоки, таблицы, ссылки, изображения, подписи, литературу и порядок элементов. Не требовать байтового равенства HTML и JSON: их канонические безопасные проекции сравниваются содержательно, без новых орфографических или типографических преобразований. Не менять исключённую подсистему дефисов/тире или её вызовы. Повреждённое/неподдерживаемое содержимое не превращать в пустую страницу для дальнейшего сохранения.

Опубликованная редакция остаётся читаемой до отдельного выпуска. Не реализовывать черновик переводом самой опубликованной записи в draft: это снимет страницу с сайта. Предпросмотр читает выбранную рабочую редакцию, не отправляет её в индекс или публичный экспорт.

### M20. Автокопии: подтверждение commit, ошибки браузерного хранилища и приватность — P0

**Основание.** `PageEditor` сбрасывает dirty в обработчике отправки, до ответа сервера, и не использует отрицательный результат локального сохранения для этого решения. В `RecoveryController` результат загрузки `{ok:false}` может быть проигнорирован; отсутствующий необязательный fallback может приводить к статусу local. На странице редактирования `savedAfterSubmit` определяется через `Boolean(query.saved)`, а контроллер использует этот флаг для очистки автокопии. Серверное удаление уже защищено actor, session, sequence и hash — эти проверки сохраняются. [R2E02–R2E04]

**Модель подтверждения.** Не считать submit, URL `?saved=1`, смену маршрута, отсутствие исключения или старый тост подтверждением записи конкретного текста. Нужен существующий либо минимально расширенный серверный receipt: идентичность пользователя/сущности/языка, операция, принятая версия и fingerprint принятого содержимого. Не доверять присланному клиентом receipt без сопоставления с серверным результатом. Параметры URL могут управлять только некритичным уведомлением, но не разрешением уничтожить восстановимую копию.

Dirty сбрасывается только для локальной версии, которую подтвердил сервер. Если во время запроса пользователь изменил A на B, подтверждение A не очищает dirty B. При известном отказе сохранить текст и ошибки полей; при потере ответа после возможного commit показать неизвестный исход и проверить операцию по устойчивой идентичности до повтора. Не создавать новую редакцию на каждый retry.

**Автоматическая очистка и явное удаление — разные намерения.** Для очистки после canonical-save доказать, что подтверждённый сохранённый снимок действительно покрывает удаляемую автокопию. Старый receipt или совпавший entityId недостаточны. Не требовать одинаковых байтов сериализаций, если существующая безопасная сериализация различается: определить проверенный канонический fingerprint и его версию. Более новая копия или другая вкладка не удаляются. Явное «Отказаться от этой автокопии» может удалить точный выбранный снимок без canonical commit, но требует отдельного намерения пользователя и сохраняет все существующие проверки точного удаления. Не пытаться решить проблему глобальным удалением всех autosave строк.

**Ошибки и гонки.** Любое `{ok:false}` из поиска recovery показывать как недоступную проверку, не как «копий нет». Ошибка `sessionStorage.getItem/setItem` не должна разрушать редактор; серверный commit и неудача записи локальной квитанции — разные результаты. Статус «локально сохранено» допустим только после явно положительного подтверждения реального локального адаптера; отсутствие функции/undefined не является успехом. Проверить quota, SecurityError, повреждённый JSON, недоступный crypto/идентификатор сессии, отказ очистки, несколько вкладок и смену locator во время ожидания ответа. Старый запрос не обновляет состояние уже другого материала. Все promise-rejection пути обрабатываются без ложного успеха.

Сохранять `lastSavedSnapshot` и sequence в правильном scope; при смене материала/пользователя старое состояние не должно подавлять новую автокопию. При доступном сервере не создавать постоянный цикл загрузки копии на каждое нажатие клавиши. Backoff и повтор ограничены; при непрерывном наборе последний снимок должен дойти после завершения активной записи.

**Приватность.** Серверная фильтрация по actor_id уже есть; не ослаблять её. Проверить существующие localStorage/sessionStorage ключи, в частности ключ страницы без пользователя. Новые ключи включают scope аккаунта, материала, локали и версии схемы; содержимое не хранится в URL, аналитику не отправляется. Для старых ключей без доказанного владельца не показывать текст следующему вошедшему аккаунту и не присваивать его текущему пользователю. Не уничтожать массово наследованные копии: обозначить недоступность автоматического безопасного восстановления и предусмотреть контролируемый путь владельца вне обычного показа. TTL и очистку на выходе согласовать с предупреждением о несохранённых правках; logout не должен публиковать или переносить данные между аккаунтами.

**Приёмка.** Повторный заход по старому URL успеха не удаляет новую автокопию; отказ браузерного хранилища не рисуется успехом; обрыв сети и поздние ответы не теряют ввод; новые состояния проверены настоящими компонентными и браузерными сценариями, а не поиском строк.

### M21. Рубрики и теги: зависимости, адреса, объединение и удаление — P1

**Основание.** Обработчик рубрик разрешает смену slug и прямое удаление с CAS; отдельная прикладная запись аудита не разбирает ошибку. Базовая схема содержит SET NULL для связи статьи с рубрикой и CASCADE для связей с тегами. Это свойства проверенных исходников; итоговые ограничения текущей схемы должны быть сверены со всеми применимыми миграциями. Outbox-триггеры уже предусмотрены, создавать их дубли не нужно. [R2E05, R2E06, R2E16]

**Матрица влияния.** До смены slug, объединения или удаления показать число и примеры зависимых опубликованных статей, рабочих черновиков, переводов, страниц/блоков, меню, исторических ссылок и редакционных фильтров. Считать по серверным связям, а не по текущей странице списка. Отдельно обозначать «проверка зависимостей недоступна»; в этом состоянии опасное действие закрыто.

Название и URL — разные поля. Простое переименование не меняет ID и slug. Явная смена URL проверяет занятые slugs, существующие alias/redirect, зарезервированные системные рубрики и используемые в сборщике/социальной публикации таблицы маршрутов. Нельзя обновить только запись categories, оставив экспорт, canonical, RU/EN и старые публичные пути в противоречии. Сформировать проверяемый план переходов со старых реальных адресов; не придумывать тысячи адресов из шаблона без связи с каталогом.

Обычная безопасная операция — скрыть/архивировать рубрику при сохранении зависимостей, если модель это поддерживает. Полное удаление непустой рубрики требует назначения целевой рубрики либо явного отказа; не полагаться на SET NULL как на удобный редакционный результат. Для используемого тега — показать влияние; объединение тегов сохраняет связи без дублей и не меняет текст статьи. История происхождения остаётся доступной. Исторические снимки не переписываются задним числом.

**Запись.** Использовать специализированную транзакцию/существующий RPC для набора связанных изменений и обязательного аудита; проверить действующие outbox-триггеры. Preview не является разрешением на будущую устаревшую запись: отправка ссылается на ожидаемые версии/план и повторно проверяет изменившиеся зависимости внутри транзакционной границы. При большой базе — возобновляемый подготовительный проход, а не тысячи записей в одном запросе Worker. Во время промежуточного переноса не публиковать половину новой схемы ссылок. Устаревший план не применяется автоматически.

Редакционные права согласовать с уже действующей моделью: не расширять editor до системного управления. UI объясняет последствия на русском; массовое подтверждение связано с точным набором IDs, действием и версией. Новый экран не запускает удаление реальных данных при проверке.

**Приёмка.** Используемая рубрика не исчезает без осознанного переноса зависимостей; URL-переходы работают в обеих локалях; конфликт версии не оставляет половину назначений; отказ записи обязательного аудита не маскируется успешным результатом.

### M22. Меню и баннеры: структура, область показа и расписания — P1

**Основание.** Меню проверяет самоссылку и версии, но в просмотренном action нет полной проверки циклов/принадлежности родителя тому же меню. Публичный `buildCmsNavigationForest` уже выводит повреждённые циклы и сирот безопасными корнями. У баннеров невалидные строки области показа отбрасываются, список обрезается до 50 до валидации; полностью невалидная область может превратиться в `/`. Время проверяется в action в основном как строка. Публичная проверка временного окна уже закрыта при невалидных границах. [R2E07–R2E09]

**Меню.** Проверить все пути записи, включая восстановление версии и прямой RPC. Родитель принадлежит тому же меню; недопустимы самоссылка, цикл любой длины и превышение поддерживаемой глубины. Две конкурентные операции A→B и B→A не должны вместе создать цикл: одной клиентской проверки недостаточно. Использовать блокировки/версию дерева в существующей транзакционной модели; старый UI не должен обходить новый инвариант.

Визуальная перестановка имеет клавиатурный эквивалент. Стабильный порядок определяется displayOrder и постоянным ID без случайного пересортирования равных элементов после refresh. Перемещение родителя учитывает поддерево. Удаление показывает потомков и выбор поддерживаемого действия: отменить, перенести потомков к допустимому родителю, удалить явно подтверждённую ветку. Само наличие FK CASCADE не заменяет подтверждение последствий. При невозможности безопасной операции ничего не менять. Публичную защиту от старых повреждённых связей сохранить, не использовать её вместо корректной записи.

**Баннеры.** Заменить молчаливую фильтрацию области показа явной валидацией каждой строки. Непустой ошибочный ввод нельзя превращать в главную страницу; превышение лимита нельзя скрывать обрезкой. Пустая область имеет отдельную ясно показанную семантику; значения по умолчанию допускаются только для действительно пустого нового выбора, а не ошибки. Грамматика шаблона согласована с `cmsPagePatternMatches`: точный путь/допустимый терминальный wildcard и границы сегментов. Не разрешать произвольные regex для исполнения на Worker. Язык `/en`, query/hash, trailing slash и percent-encoding обрабатываются одинаково в админке и renderer.

Добавить read-only предпросмотр охвата: конкретный публичный маршрут + локаль + дата/время → будет ли показан баннер и почему. Не утверждать, что весь каталог проверен, если проверены только примеры. Обложки desktop/tablet/mobile, fallback и фокус должны соответствовать уже существующему renderer; отсутствие варианта не приводит к случайной подстановке другой книжной обложки. Не менять текущий art direction публичного сайта.

Время: единый контракт M04, startsAt < endsAt при обеих границах, разрешённые открытые интервалы, точная граница окончания (endsAt исключается), явная IANA-зона и DST. Проверить временные поля Site Studio вместе с баннерами; runtime-default `new Date(naiveString)` не должен определять смысл редакторского времени. Не сдвигать уже записанные instants. Будущие баннеры не публикуются раньше, истёкшие не остаются из-за устаревшего snapshot; способ временной доставки сверить с существующим build/runtime, не добавлять новый cron без необходимости.

**Приёмка.** Невалидная область отклоняется без изменения прежней; циклическая структура не сохраняется, в том числе конкурентно; неверная дата не приводит к успешному тосту; одинаковый маршрут/момент даёт одинаковый результат в preview и публичном коде.

### M23. Загрузка файлов: граница HTTP, восстановление Storage и регистрация — P0/P1

**Основание.** Media Route Handler сначала разбирает multipart, а ограничение `File.size` проверяет уже после этого; разбор расположен вне его основной try/catch. В обоих просмотренных upload Route Handlers нет локальной явной проверки Origin, что требует проверки общей защиты, но не доказывает эксплуатацию production. MIME/размеры/пиксели и SHA-256 изображений уже проверяются. Шрифты адресуются по содержимому и намеренно не удаляются сразу при ошибке регистрации: файл может использовать другая конкурентная операция. [R2E10, R2E11]

**Граница запроса.** Отдельно проверить обычные Route Handlers: встроенные гарантии Server Actions не переносить на них по предположению. При cookie-auth защищать записывающие запросы согласно реальному origin/CSRF контракту проекта; принимать только проверенный собственный origin/разрешённый адрес, корректно обрабатывать proxy-host и missing/null Origin. Не считать произвольный X-Forwarded-Host доверенным. Сохранить legit same-origin upload для текущей конфигурации `ADMIN_BASE_PATH=/` и проверенного `/admin`, не включать широкий CORS wildcard и не требовать GET-мутаций. Проверить сторонний сайт и недоверенный sibling subdomain как разные случаи в изолированной среде.

Ограничить общий объём запроса, число полей/файлов и обработку до неограниченного буферизования там, где поддерживает runtime. Один Content-Length недостаточен: он может отсутствовать. Если runtime/adapter уже гарантирует hard limit, документировать и испытать его на фактическом Cloudflare/OpenNext preview, а не дублировать опасный парсер. Ограничения body/file/pixels/multipart overhead согласованы; client limit оставляет обоснованный запас, серверная граница остаётся окончательной. Ошибки multipart, неподдерживаемого MIME, повреждённых размеров, 413/415/422/429/503 дают понятный результат без сырого ответа провайдера.

Не ослаблять sniffing контейнера, ограничение пикселей, SHA, запрет SVG/GIF или удалённых шрифтов, если они действуют в текущем контракте. Не называть проверку заголовка полным антивирусным сканированием. Не загружать/не передавать сами шрифты в отчётный пакет. Если нужна дополнительная тяжёлая обработка, сначала оценить бюджет Worker и использовать существующий pipeline, не добавлять неограниченную декомпрессию.

**Восстановимая операция Storage + БД.** Одна SQL-транзакция не объединяет объектное хранилище и регистрацию. Сначала проверить существующие lifecycle/cleanup workflows. Расширить их минимальной записью операции/резервацией, устойчивой идентичностью запроса, состояниями prepared/uploaded/registered/failed/cleanup-needed либо эквивалентом. После обрыва различать сохранённый объект без записи, зарегистрированный файл без ответа и известный отказ. Retry сначала сверяет операцию и не создаёт копии без необходимости. Пользователю показать завершённые и неуспешные файлы по отдельности.

Компенсация учитывает тип адресации и ссылки: для нового случайного image-path допустима безопасная очистка своего неиспользуемого объекта, если принадлежность и отсутствие зависимостей подтверждены; для content-addressed font-path нельзя удалять общий объект из-за чужой ошибки регистрации. Cleanup имеет grace period, повторную проверку ссылок непосредственно перед удалением, журнал и ограниченные повторы. Упавшая cleanup не скрывается, но не выдаётся за провал уже принятой записи. Тестовые файлы не распространяют за собой real user data.

**Конфиденциальность.** Статус «черновик материала» не делает уже публичный Storage URL секретным. Проверить фактические bucket policies, использование подписанных ссылок и previews. Не переводить весь существующий публичный bucket в private и не ломать текущие изображения. Для действительно конфиденциального нового вложения нужен поддерживаемый изолированный режим; если его нет, явно не обещать приватность.

**Приёмка.** Защита работает на настоящем Route Handler; malformed/oversized запрос не валит обработчик; retries/crash recovery не теряют зарегистрированные файлы; конкурентная регистрация шрифта не удаляет общий файл; существующие изображения и публичные ссылки не изменены.

### Уточнение R3: контракт приватных ответов
[R3E07, R3E08, R3E10] No-store в успешной ветке конкретного API не доказывает те же заголовки у 401/403/503, redirect, malformed DTO или prefetch/RSC. Проверить итоговый ответ после реального middleware и deployment proxy, не только исходник отдельной функции. Если общая защита уже покрывает ветки, сохранить её и добавить тест, не дублировать конфликтующие политики во всех обработчиках.

Содержимое ошибок — безопасный код и correlation ID, без токенов восстановления, секретов или приватных payload. Проверку кеша проводить разными тестовыми аккаунтами; безопасный cache публичных ассетов не отключать из-за приватности admin JSON.

### M24. Тексты сайта и шаблоны: версии, переменные и отказ перевода — P1

**Основание.** В `saveSiteCopyAction` перевод изменённых строк может выполняться до `save_site_copy_block`; ошибка runtime-gate/провайдера прерывает сохранение исходных правок. Защита ручного EN и CAS уже есть. В действиях Site Studio время преобразуется через `new Date(candidate)`; семантику зоны нужно согласовать. Редактор статей поддерживает personal/shared templates: их права и текущую реализацию следует сверить на HEAD, а не предполагать готовность всех операций. [R2E12, R2E13, E05]

**Надёжное сохранение.** Доступность переводчика не должна быть условием сохранности введённых RU/EN. До внешнего запроса обеспечить сохранение рабочего снимка/задачи в действующем защищённом контуре. Если политика требует согласованный bilingual release, отделить сохранение черновика от публичного применения: не выпускать неготовую половину. Не заменять ранее опубликованный EN пустым результатом и не пересоздавать вручную редактированную строку. Ошибка перевода оставляет явную задачу на повтор и исходный ввод. Долгий перевод не должен удерживать один HTTP-запрос; использовать M07. Существующий kill switch, выбор моделей, лимиты и запрет реальных платных вызовов в текущем задании сохраняются.

**Контракт строки.** Для каждого реально управляемого ключа показать назначение, место использования, локаль, исходное значение, override и происхождение. Не начинать массовый перевод или переименование ключей. Действия «сбросить override/наследовать» и «задать намеренно пустое значение» различаются там, где пустое значение разрешено. Если контракт ключа запрещает пустоту, объяснить это до сохранения, а не убирать строку молча.

Плейсхолдеры, ICU/plural/rich-text tokens проверять только в тех строках, где эти механизмы действительно применяются. Нельзя вводить фиктивную обязательную ICU-схему для простого текста. Сохранить именованные переменные, допустимые теги и экранирование; сравнить обязательные параметры RU/EN и справочника. Не разрешать подмену `__proto__`/зарезервированных объектов при работе с динамическими словарями; существующие произвольные `interface.*` ключи проверить по назначению, а не отключить все кастомные ключи. Отчёт об осиротевшем override не является разрешением его удалить.

При разных формах, редактирующих один системный блок, сохранить неотправленные поля. Патч имеет явный набор изменённых ключей; пустой набор не очищает всё. CAS/проверки выполняются в транзакции. Слияние неконфликтующих ключей допустимо только с проверенной семантикой и сохранением ручного происхождения, иначе показать сравнение. Не хранить несколько равноправных блоков с одним systemKey, выбирая «последний» как случайный master; сверить уникальный контракт в RPC и миграциях.

**Шаблоны.** Проверить сохранение, применение и удаление personal/shared templates в существующих действиях: приватный шаблон не читается другим аккаунтом; редактор не меняет чужой shared без соответствующего права; удаление шаблона не меняет уже созданные статьи. Применение вставляет копию после понятного выбора/preview, не подменяет существующий текст по умолчанию. Санитизация та же, что для обычного ввода. Смена шаблона не выдаёт прежние проверки прав/фактов за подтверждение нового содержимого.

**Приёмка.** При недоступном переводчике правки восстановимы; placeholder mismatch обнаруживается до применения; reset/inherit работает без удаления соседних ключей; права personal/shared проверяются сервером; неприкосновенный текст и нормализаторы не изменены.

### M25. Литературная повестка: интеграция с календарём и социальной доставкой — P1

**Граница пользователя.** Развивать существующий блок «Литературная повестка», не создавать новостные статьи, новую самостоятельную новостную витрину, вторую энциклопедию или новую календарную систему. Календарь считается существующей функцией: здесь проверяются контракты его данных, а не переделка интерфейса. Названия внутренних legacy-роутов `/literary-news` могут сохраниться для совместимости. Отдельное расширение корпуса источников/новостей не подменяет реализацию редакционного цикла.

**Основание.** Просмотренная очередь — приватные KV-снимки найденных held-кандидатов; сама по себе она не является журналом одобренных событий. Существующий social worker обслуживает статьи, по умолчанию Дзен, а VK зависит от отдельного флага. Это не доказательство готовой доставки повестки в Telegram/VK. [R2E14, R2E15]

**Карточка и календарь.** В M10 выбрать один master одобренных карточек и версии; KV остаётся снимком обнаружения. Карточка хранит discoveredAt, publishedAt источника и отдельно проверенную дату/интервал события с её точностью, при необходимости зоной и ссылкой на доказательство. Не ставить фиктивное 00:00 UTC, если известен только день. Премия, выход книги, фестиваль, литературная дата и новостной комментарий не должны автоматически получать один календарный тип. Неизвестная дата остаётся неизвестной и не допускается в точный календарный слот. Исправление события обновляет его существующий календарный ID/связь, не создаёт двойника; отзыв согласованно убирает публичную карточку и календарную проекцию.

Результаты сборщика — недоверенный ввод. URL/HTML/заголовки/ответы моделей не могут выдать себе редакционное одобрение, командовать инструментами или изменять настройки; возможные embedded instructions игнорируются. Проверка источника относится к источнику и моменту, не ко всем его фактам. Массовое принятие не заменяет подтверждение содержания; каждый переход к публикуемому состоянию связан с редакцией и актором. Дубли объединяются по проверенному событию с сохранением источников, а не просто похожему заголовку. Редакторское решение живёт дольше временного снимка held-очереди.

**Социальная доставка.** Предусмотреть интеграцию опубликованной карточки повестки с действующим механизмом внешней доставки, не копируя её в articles ради повторного использования старого worker. Тип источника (`article` / `literary_agenda`) и channel destination входят в идентичность операции. Уважать существующие выключенные каналы и отдельные права: это задание не разрешает отправку реальных сообщений или включение флагов. Если готовой интеграции нет, реализовать тестируемый адаптер/очередь и понятное состояние NOT_CONFIGURED до подключения, не рисовать успешную доставку.

Перед запрошенной отправкой показать точный канал, язык, текст/картинку/ссылку и редакцию, которая уже подтверждена на публичной повестке. Черновик, held или неудавшийся выпуск не отправляются. Реальная автоматизация возможна только в ранее разрешённом режиме и для уже опубликованных подходящих карточек; новый режим по умолчанию выключен. Заголовки/текст не генерируются скрытно от владельца.

Идемпотентность относится к источнику+редакции+платформе+каналу+намерению. Сетевой timeout после отправки означает unknown outcome, а не разрешение безусловно отправить ещё раз. Если API предоставляет idempotency key/remote ID, использовать их; иначе reconciliation или ручное решение с предупреждением о возможном дубликате. Успех RSS-подготовки не равен публикации на платформе. Правка после отправки — отдельная update-операция для известного remote ID, если поддерживается; отзыв не обещает мгновенное удаление у провайдера. Unsupported update/delete явно требуют ручного действия. В отчёте не показывать секреты назначения/доступа и приватные API-ответы.

**Приёмка.** Одобрение повестки, календарная проекция и внешняя доставка ссылаются на одну редакцию; статистика не считает held и просто найденные заголовки опубликованными. Provider-mock проверяет отправку/повтор/отзыв без реальных сообщений; отдельная реальная проверка подключения остаётся NOT_RUN/BLOCKED без разрешения.

## R2E21. Первичные технические источники

Документация использована для контрактов безопасности и тестирования, не для вывода о конкретном production-состоянии проекта. Версии runtime и библиотек берутся из самого репозитория.

Supabase MFA: `https://supabase.com/docs/guides/auth/auth-mfa` — UI второго фактора не заменяет backend/RLS enforcement.
Next.js data security: `https://nextjs.org/docs/app/guides/data-security` — проверка чувствительных операций и данных у их серверной границы.
OWASP CSRF: `https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html` — защита cookie-auth мутаций, origin/proxy и дополнительные меры.
OWASP File Upload: `https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html` — несколько независимых ограничений загрузки вместо доверия MIME/имени.
Cloudflare KV: `https://developers.cloudflare.com/kv/concepts/how-kv-works/` — модель согласованности не превращает KV в транзакционную блокировку.
PostgreSQL isolation: `https://www.postgresql.org/docs/current/transaction-iso.html` — проверки конкурентных инвариантов в транзакциях; это не запрос обновить PostgreSQL проекта.
Playwright authentication: `https://playwright.dev/docs/auth` — изоляция тестового auth-state, который нельзя коммитить как обычный fixture.

## Исправления формулировок предшествующего аудита

1. Отдельный вызов requestPublicBuild в action не означает отсутствие durable записи: SQL уже содержит outbox triggers. Остаются проверка эффективной схемы, аудит и обработка fast-dispatch receipts.
2. Публичное меню уже защищено от циклов; доработка — write-side инварианты и операции с поддеревом, не удаление runtime-защиты.
3. Наличие public URL не доказывает ни права на картинку, ни её приватность в черновике.
4. Ограниченная выборка досье доказывает ограничение интерфейса, не потерю старых данных.
5. Количество блоков и сценариев — объём задания, не степень выполненности приложения.
