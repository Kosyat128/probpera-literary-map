## Как принимать технические решения

Приоритеты: P0 — доступ и сохранность; P1 — достоверность и завершение основных процессов; P2 — удобство, измерения, развитие. P2 тоже входит в задание, но не должен отодвигать P0/P1.

Для каждого пункта указать: подтверждено в актуальном коде / уже исправлено / требует исполнения / не относится к текущей архитектуре. Уже работающий механизм переиспользовать. «Не относится» требует ссылки на код и объяснения; это не способ молча убрать требование. Не считать ограничение вывода доказательством потери данных. Не превращать предположение о производительности в установленную причину тормозов.

Новые имена DTO, RPC и статусов ниже являются проектными предложениями, а не утверждениями об их наличии. Сначала найти существующий эквивалент и расширить его. Не создавать универсальный framework для всех редакционных сущностей: достаточно тонких общих контрактов и специализированных адаптеров.

Тексты интерфейса — понятный русский без названий внутренних стадий разработки. RU/EN относятся к содержимому и предпросмотру; не начинать отдельный полный перевод самой админки, если это не её текущий контракт.

## Общие контракты, чтобы разделы не расходились

### Результат операции

Согласовать существующий тип и расширить его, если нужно:

- outcome: success / rejected / conflict / dependency-unavailable / unknown-outcome;
- operationId/correlationId и server revision при подтверждённой записи;
- fieldErrors для валидации; безопасный errorCode; retryable с конкретной семантикой;
- publicationState отдельным полем, не частью расплывчатого «успешно»;
- исходные значения не заменяются empty/default на ошибке.

Это не строгий новый API, который нужно внедрить во все файлы разом. Разрешены адаптеры для старых контрактов. Для GET ошибки HTTP/SSR и для Server Action формы обрабатываются подходящим существующей архитектуре способом.

### Версия и подтверждение

Любой audit/review/preview/release ссылается на конкретную редакцию. expectedRevision/updated_at проверяется сервером в момент записи; client role, hidden fields, raw JSON и отметка «проверено» не являются источником прав. Content hash для опубликованного snapshot не включает случайные временные поля и вычисляется детерминированно. Токены сравнения не теряют точность при передаче через JS.

### Авторские материалы и безопасность

Не превращать «сохранить без изменений» в массовое редактирование. Новый UI не генерирует содержание, не приводит имена/названия/источники к новым вариантам. При этом не отключать санитизацию небезопасного HTML: исходный безопасный контент и опубликованная проекция должны проверяться отдельными контрактами. Ранее существующее исключённое поведение учитывать только как точечный baseline, не как blanket-разрешение на изменения.

### Источники истины

Один master для каждого вида изменяемых данных. Snapshot/кеш/экспорт имеют явное происхождение и версию; недоступность master не даёт права перезаписать его старым snapshot. Не рассчитывать на синхронность KV между регионами. Канонические IDs книг/авторов сохраняются, а новые формы не создают локальные заменители.

## Дополнительные сквозные контракты R2 FINAL

### C01. Раздельные состояния одного изменения

У сущности могут независимо существовать локальный ввод, серверная автокопия, рабочий черновик, одобренная редакция, принятый запрос на выпуск, публичный snapshot/live-редакция и внешняя социальная публикация. Общая зелёная метка не заменяет эти состояния. Идентичность редакции не равна Git SHA; receipt принадлежит конкретной операции и набору данных. Текущий пользователь вправе видеть только разрешённые ему состояния.

### C02. Граница подтверждения

Подтверждённая сервером запись и неизвестный сетевой исход различаются. Восстанавливать результат запроса можно по устойчивому operationId с проверкой actor/entity/intent/expectedVersion; повтор с другим payload при том же ID отклоняется или явно конфликтует. Не хранить для этого бесконечные копии полных текстов в audit. `?saved=1`, число попыток и отсутствие ошибки в браузере не являются серверной квитанцией. Автоочистка требует доказанной принятой редакции; явный discard — отдельное намерение.

### C03. Outbox и целостность snapshot

Сохранить действующие after-mutation triggers, append-only события и совместный RU/Premium export. Идемпотентность команды не удаляет отдельные события разных транзакций. Нельзя подтверждать события по одному «последний ID» без проверки того, что снимок действительно их включает; проверить существующий high-water/content-hash протокол, особенно поздние commit. Группировка запросов в UI/одну сборку не уничтожает связь с исходными редакциями. Разрешённая внутренняя инвалидация от draft не равна его публикации.

### C04. Авторские тексты и представление

Никаких новых нормализаций, генераций или массового ремонта контента. HTML и JSON имеют согласованную безопасную проекцию и сохранённое происхождение. Утрата/повреждение одного представления — ошибка либо legacy-режим, не разрешение на пустую перезапись. Сохранить санитизацию; не переводить опасный HTML в разрешённый ради совпадения байтов. Исключение по дефисам/тире действует точечно и не допускает изменения смежного содержания.

### C05. Публичность не определяется видимостью кнопки

RLS/RPC/Server Actions/Route Handlers/Storage/preview/search/export проверяются отдельно. Закрытые drafts, источники прав и полный банк spoiler-вариантов не попадают в публичные payload/сборки/кеши. Наличие public URL файла означает отдельный режим доступа, даже если статья пока draft. CSS-hidden, noindex и подписанная надпись не являются контролем доступа.

### C06. Удаление и замена

Для каждой разрушительной операции определить dependencies, возможность восстановления и точные последствия до её выполнения. Версия и набор выбранных IDs входят в подтверждённое намерение; сервер проверяет их повторно. Никаких wildcard delete, молчаливого cascade или удаления shared content-addressed файла из-за ошибки другой операции. Soft-delete не обещает недоступность уже публичных внешних копий. Audit append-only, неоднозначный исход допускает reconciliation, не слепой повтор.

### C07. Источник истины и перенос

Один master на каждый тип данных. При переносе новостей/настроек есть baseline, проверяемый импорт, сверка количества/IDs/редакций, затем контролируемый switch и запрет двусторонних независимых записей. Snapshot не пишет обратно поверх master. Existing data, direct-card URLs и утверждённые публичные блоки не переносятся только ради новой структуры админки.

### C08. Время и срок действия

Точный instant хранится в UTC; значение с известным только днём хранится как date-only; неизвестная дата не подменяется текущей. Ввод времени имеет явную IANA-зону, валидный offset и обработку DST; не сдвигать ранее записанные instants. Срок прав/lease/self-test/backup применим к конкретному виду события и не обобщается одним TTL. Статус UNKNOWN не маскируется FAILED/OK.

### C09. Неподдерживаемые возможности

Не отключать gates, чтобы завершить форму. В частности, public dossier full-text/quote/media/articleReuse не включаются без необходимых уже одобренных прав и схемы; в проверенном снимке они запрещены. Канал социальной отправки без конфигурации не становится работающим. Capability-off не означает, что фиктивный успешный ответ допустим. Для новых независимых возможностей — явные состояния и безопасная интеграция, не неподключённая кнопка с обещанием результата.

### C10. Бюджет и исполнение

Сначала короткий baseline и P0, далее реализация вертикальными проходами: форма → action/API → DB/worker → обратная связь → регрессионные тесты. Не проводить весь повторный аудит прежде первого исправления. Каждая новая механика должна закрывать доказанный сценарий; не вводить event sourcing, CQRS, вторую очередь, тяжёлый графовый движок или внешний сервис без необходимости. Сохранить использованные runtime/версии dependencies, сначала проверить lockfile и commands. Наличие этой инструкции не делает выполнение бесплатным по лимиту Codex.

### C11. Доказательство завершения

У каждого теста есть ID, предусловия/шаги, ожидаемый результат, требуемый уровень и исходный NOT_RUN. Фактический результат отдельно содержит команду, дату, SHA/tree, окружение, outcome/exitCode, artifact и область mock. Source-string test не доказывает поведение DB или браузера; локальное выражение не доказывает работу production. BLOCKED/NOT_RUN/WAIVED с явным решением не считаются PASS. Смена diff требует повторной проверки затронутых сценариев. Не произносить «100% готово», пока не выполнены все применимые критерии.

### C12. Границы текущей задачи

Разрешена подготовка и реализация кода в безопасной ветке и изолированных тестах, но не production-мутации, включение отправки/платных вызовов или произвольный merge. Существующий доступ инструмента не равен разрешению на действие. При внешнем блокере продолжать независимый безопасный код и тесты; остановить только опасную часть. Задание окончательное по текущему обследованному объёму, а не гарантия отсутствия новых требований или будущих дефектов.


## Дополнение R3: строгость результата без переусложнения


## Одно исправление — одна проверяемая цепочка
Для каждого модуля сначала выбрать текущий дефект/незавершённый сценарий, затем пройти UI → action/endpoint → RPC/storage → результат → проверка. Смена подписи без работающего backend, фиктивный success, кнопка «в разработке» и заглушка не закрывают требования. Не заменять реализацию документацией.

Для нового code defect фиксировать воспроизведение исходного поведения и исправленного на одинаковом fixture. Для существующего работающего механизма достаточно подтверждения поведения и сохранения regression test; не переписывать его ради другого стиля. Каждая заявленная исправленная ошибка имеет ссылку на конкретный diff и тест. Сам факт зелёной сборки не доказывает все сценарии.

## Формы данных между слоями
Фиксировать для затронутых RPC фактическую сигнатуру, returned SQL type, пример обезличенного результата, клиентский parser/DTO и callers. scalar UUID не row {id}, bigint не безопасный произвольный JS number, null не пустой успешный объект. Валидировать до следующего побочного действия. JSON parsing success не означает валидность бизнес-данных. Неподдерживаемый result возвращает безопасную ошибку и не даёт полномочий на compatibility fallback.

## Статусы и доказательства
TASKS.json и ACCEPTANCE_RESULTS_TEMPLATE.json в поставляемом пакете — исходный NOT_RUN. Они не описывают сделанные изменения приложения. Рабочие результаты вести отдельно с полями: test_id, status, code_fingerprint (HEAD + digest релевантного diff), environment, level, command, exit_code, checked_at, evidence_path, mocked_dependencies, limitations. Для DB/E2E PASS соответствующий dependency не замокирован. Скриншот без прохода action не доказывает DB; source substring не доказывает реальную функцию.

Допустимы NOT_RUN, RUNNING, PASS, FAIL, BLOCKED. NOT_APPLICABLE только с проверяемым архитектурным основанием и перечнем покрытого эквивалентного сценария; это не PASS и не способ исключить желаемую функцию. Для возможности, которой в текущем коде ещё нет, корректен PLANNED/BLOCKED, но не NOT_APPLICABLE из-за отсутствия реализации. Production/paid/social tests не выполняются без отдельного разрешения; вместо них подтверждаются безопасные локальные границы с явно указанным mock.

Близкие criteria могут ссылаться на один тест. M11-T02/M11-T07 — один failure family (unknown usage graph → no purge), сохранить оба ID в mapping для прежних checkpoint. Число criteria не является числом независимых автотестов. Не создавать дубликаты ради количества.

## Граница выпуска
