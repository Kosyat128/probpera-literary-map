# Media Studio: жизненный цикл и восстановление

## Гарантии Phase 4

- Объекты в Storage неизменяемы: новая загрузка создаёт новый `mediaId` и новый
  путь, а существующий файл не перезаписывается.
- SHA-256 хранится у ресурса и используется для поиска дубликатов и защиты
  операции замены.
- Граф зависимостей охватывает текущие статьи, переводы, страницы, обложки,
  Open Graph, главную страницу, баннеры, ревизии и автосохранения.
- HTML `data-media-id` и TipTap JSON должны содержать одинаковые изображения:
  UUID, адрес, alt/decorative-признак и кратность повторений. Повреждённый либо
  расходящийся документ отклоняется до канонической записи.
- Корзина является мягким удалением. История, метаданные и Storage-объект
  сохраняются. Безвозвратное удаление доступно только владельцу отдельным
  staged-протоколом после 30 дней хранения и полной проверки зависимостей.

## Безопасная замена

1. Загрузить новый файл и убедиться, что у него есть SHA-256 и подтверждённый
   статус прав.
2. В Media Studio указать UUID старого и нового ресурсов и открыть предпросмотр.
3. Проверить текущие зависимости и выбрать нужные либо все текущие ссылки.
4. Подтвердить замену. RPC повторно сверяет версии ресурсов и полный снимок
   зависимостей, блокирует конкурентное изменение и выполняет замену атомарно.
5. Убедиться, что аудит содержит `media.current_usages_replaced`, а новый ресурс
   показывает ожидаемые зависимости.

Ревизии и автосохранения при замене не переписываются. Старый объект остаётся
доступным для восстановления прежней версии. Если зависимости изменились между
предпросмотром и подтверждением, операция завершается без частичной записи.

## Корзина и восстановление

- Перед перемещением в корзину Media Studio показывает число текущих и
  исторических зависимостей. Ресурс с активным использованием нельзя считать
  безопасным сиротой только по внешнему виду каталога.
- Восстановление проверяет наличие точного объекта в `storage.objects`. Если его
  нет, операция прекращается с ошибкой и не создаёт ложную активную запись.
- Поиск сирот выполняется через фильтр нулевых текущих зависимостей; ревизии и
  автосохранения всё равно остаются видимыми в подробном графе.
- Безвозвратное удаление показывается только владельцу и только для ресурса,
  который находится в корзине не менее 30 дней. `prepare_media_asset_purge`
  блокирует ресурс, повторно проверяет текущие, исторические, autosave- и
  lineage-связи и возвращает точный bucket/path с одноразовым токеном. Приложение
  удаляет ровно этот Storage-объект, затем `finalize_media_asset_purge` ещё раз
  проверяет токен, версию и зависимости перед удалением строки метаданных.
- При ошибке Storage приложение пытается отменить подготовку. Если ответ
  неоднозначен и объект уже исчез, отмена fail-closed не выполняется: повторное
  действие владельца получает тот же токен и безопасно продолжает финализацию.
  Прямой `DELETE` таблицы и массовый Storage purge не предоставляются.

## Массовые операции

- Для массовой правки сначала отмечают карточки, затем отдельно включают только
  те поля метаданных, которые нужно изменить. Сервер ограничивает пакет,
  проверяет UUID и `updated_at` каждого ресурса, не перезаписывает конкурентные
  изменения и пишет единое событие `media.bulk_metadata_updated` со списком
  реально обновлённых ресурсов.
- Очистка сирот всегда состоит из двух действий: **подготовить предпросмотр**,
  проверить список и явно подтвердить применение. Перед записью сервер заново
  получает тот же ограниченный снимок, проверяет текущие и исторические связи,
  версии строк и общее число кандидатов. Изменившийся снимок отклоняется.
- Каждый подтверждённый ресурс дополнительно проходит транзакционную проверку
  `trash_media_asset`. Результат — только обратимая корзина; Storage-объекты не
  удаляются. Если отдельный ресурс успел получить связь, он безопасно
  пропускается и отражается в результате и аудите.

## Применение в production

Миграция `20260830_media_studio_lifecycle.sql` включена в штатный production
migration plan. Применять её следует только workflow reconciliation: он проверяет
точный SHA `main`, контрольную сумму одобренного плана, создаёт и восстанавливает
зашифрованную резервную копию, валидирует миграцию изолированно и после записи
сравнивает `get_editorial_schema_health()` с ожидаемым контрактом.

Не запускать SQL вручную поверх production и не менять контрольную сумму в
workflow без повторного review самой миграции. При несовпадении схемы, SHA или
контрольной суммы reconciliation обязан завершиться до mutation.
