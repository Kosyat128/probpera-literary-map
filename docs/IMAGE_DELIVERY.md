# Public image delivery

Published article and CMS source URLs remain editorial records. The presentation layer resolves an exact source URL through `src/data/imageDelivery.generated.json`, selects a local rendition and supplies intrinsic dimensions and `srcset`. Full-resolution viewing selects the largest rendition. Credits, links, captions, focus positions and original content hashes are preserved.

The browser imports `src/data/imageDelivery.initial.generated.json`: a lossless table of shared URL prefixes, unique image entries and rendition suffixes for covers, cards, CMS content and backgrounds. Only images used exclusively inside article HTML belong to `src/data/imageDelivery.articles.generated.json`, a dependency of the existing lazy article reader. That module registers every article rendition before the reader first renders or sanitizes HTML. The first image needs no separate manifest request and there is no intermediate external-image render. CMS pages, homepage HTML and unknown provenance contexts stay in the immediate table. The complete URL map above remains the offline/static-build audit contract; preparation writes all formats and `assets:images:check` verifies their exact partition and union. Tests compare every source, variant and full-resolution reverse lookup under root and subdirectory base paths, including a reverse cache initialized before the article module loads.

`scripts/prepare-public-images.mjs` inventories article bodies in both languages, cover fields, CMS content and site backgrounds. It downloads with bounded concurrency and retries, validates decoded input, deduplicates by SHA-256 and produces proportional renditions at useful widths. It measures each raster rendition against the configured 2.5 MiB production file limit. If quality-90 WebP exceeds that limit, preparation tries lower quality at the same dimensions, then proportionally reduces the dimensions until the encoded output fits. The encoder starts from the source pixels for each attempt and preserves orientation and transparency. A smaller, compatible original that fits can supply the full-size rendition directly. Vectors and animations retain their original bytes and produce a file-specific error when those bytes cannot fit.

Use `npm run assets:images:prepare` after changing published images. The normal snapshot build runs preparation and verification automatically. Existing committed provenance and renditions are reusable without downloading everything again on a clean checkout. Changed local originals invalidate their derivative; `--refresh` explicitly refreshes remote originals. `npm run assets:images:check` checks coverage, manifest consistency and output checksums. Provenance and any unavailable sources are recorded in `reports/public-image-delivery.json`.

Production Pages caches verified source bytes for immutable public editorial-media objects in the frozen site inventory. Each build checks the checksum and size before reusing a source. It saves newly verified originals after the build attempt and before the performance audit so a retry can reuse the same bytes.

Use `publicImageAttributes` for content images and `publicImageUrl` for backgrounds or canvas textures. The resolver honors the site's base path and supports both original URLs and rendition URLs. Image-error handlers must remove `srcset` before assigning a fallback. Static article pages use the same selection model; external publication feeds keep their original media URLs.

Article illustrations load lazily with reserved geometry. The visible article cover remains eager and receives high fetch priority. These choices follow the browser guidance on [image loading and dimensions](https://web.dev/articles/browser-level-image-lazy-loading) and [fetch priority](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/fetchPriority).

The 3D article book opens without waiting for every remote illustration. Its cancellable image queue retries transient failures and updates page textures after an image arrives, retaining the current page, canvas and reading progress. Page texture updates wait until page-turn motion settles. Pending and failed illustrations have distinct states and retain their semantic text-view image.

CMS image uploads use the shared browser optimizer and inspect actual file headers. The editor first tries to retain native dimensions and uses high-quality WebP when it is smaller. Oversized static JPEG, PNG and WebP images get a bounded adaptive pass using the original pixels. Compression is adjusted first when the file is close to the cap, and further attempts reduce dimensions proportionally when needed. The browser verifies the actual 3.8 MiB file cap and shows the resulting size and dimensions. WebP within the cap, AVIF, supported animation and smaller originals retain their bytes. Server validation checks actual format and dimensions independently of the filename and submitted MIME type.

Existing writer portraits and book-cover thumbnails already have separate optimized delivery pipelines. Globe textures keep their reviewed desktop/mobile variants and spatial alignment.

The release sends fewer overlapping responsive variants for illustrations used exclusively in article bodies. A 1280px or 1920px intermediate can be omitted when the next rendition is at most 25% wider and at most 25% larger in bytes. When the projected output exceeds the total byte or file limit, the build measures and removes further optional intermediate variants until it fits or exhausts the safe choices. It first tries retained substitutes at most 25% wider and only then allows up to 50%. The substitute may add at most 50% to the bytes a reader would download for that image width. Each illustration keeps its largest rendition and available mobile and thumbnail sizes. Shared renditions used for covers, other site surfaces or direct authored links stay available. Replacing the last reference to an image removes its old generated renditions from the build copy after their bytes match the prior inventory. The source images, stored renditions and author links are preserved.

The release performance gate measures the published illustration archive separately from the application. Its limits are 1,900 distinct source URLs, 4,200 files and 640 MiB. Removing an optional variant reduces files and bytes. The exact source inventory still includes every editorial image. Only exact `media/optimized/` outputs authorized by completed provenance, with matching delivered sizes, receive this allowance. Unknown, missing or conflicting files fail the gate. Image preparation independently verifies output checksums and dimensions. The entire published site also has a 900,000,000-byte ceiling, below the [GitHub Pages 1 GB limit](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).
