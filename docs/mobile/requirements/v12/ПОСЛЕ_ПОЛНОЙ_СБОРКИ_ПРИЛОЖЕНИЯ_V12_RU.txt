2. ПРОВЕРЬТЕ ФИНАЛЬНЫЙ СТАТУС
======================================================================

Допустимый статус перед вашими действиями:

`READY_INTERNAL`
или
`DRAFT_UPLOAD_READY`
или
`BLOCKED_OWNER_INPUT`
или
`BLOCKED_STORE_ACCOUNT`
или
`BLOCKED_SIGNING`
или
`BLOCKED_LEGAL`
или
`BLOCKED_RIGHTS`

Расшифровка:

READY_INTERNAL
- вся внутренняя работа завершена;
- нужны внешние аккаунты, secrets, юридические решения и отправка.

DRAFT_UPLOAD_READY
- всё внутреннее готово;
- можно разрешить загрузку черновиков в магазины.

BLOCKED_OWNER_INPUT
- заполните только указанные поля одного owner-файла.

BLOCKED_STORE_ACCOUNT
- необходимо создать или подтвердить аккаунт магазина.

BLOCKED_SIGNING
- нужно поместить production signing key/certificate в защищённое
  хранилище.

BLOCKED_LEGAL
- требуется ваше или юридическое утверждение подготовленного документа.

BLOCKED_RIGHTS
- требуется документ на конкретный материал либо утверждение его удаления.

Недопустимо принимать результат как готовый, если status =
`BLOCKED_INTERNAL`.

Результат должен либо подтвердить готовность, либо показать один короткий

4. ДОБАВЬТЕ SECRETS В ЗАЩИЩЁННОЕ ХРАНИЛИЩЕ
======================================================================

Используйте готовый файл:

`92_OWNER_SECRETS_SIGNING_MATRIX.csv`

В нём перечислены названия secrets, но не их значения.

Обычно понадобятся:

APPLE
- App Store Connect Key ID;
- Issuer ID;
- private .p8 key;
- Apple Team ID;
- signing certificate/provisioning configuration.

GOOGLE PLAY / ANDROID
- service account JSON с минимальными правами только на приложение;
- Android upload keystore;
- alias;
- пароли keystore/key;
- подтверждённый fingerprint.

RUSTORE
- Public API token;
- signing data/fingerprint;
- RuStore Pay merchant/project secrets.

WEB/PWA
- PSP API secret;
- webhook secret;
- production backend secrets.

Хранение:

- GitHub Actions Secrets;
- защищённое серверное secret storage;
- Apple signing system;
- зашифрованный password manager;
- отдельная офлайн-резервная копия signing keys.

Никогда не храните production secrets:

- в Git;
- в обычном TXT;
- в чате;
- в screenshots;
- в публичном облаке;
- только на одном компьютере без резервной копии.

После добавления secrets выполните подготовленную проверку ссылок на них.
Команда не должна выводить сами значения.

10. APP STORE — ЧТО СДЕЛАТЬ
======================================================================

1. Войдите в Apple Developer / App Store Connect.
2. Проверьте юридического владельца и Team ID.
3. Примите актуальные соглашения.
4. Завершите banking и tax.
5. Создайте/проверьте Bundle ID и запись приложения.
6. Проверьте DSA trader status, особенно для ЕС.
7. Установите ненулевую цену приложения.
8. Выберите SAFE_INITIAL territories.
9. Вставьте подготовленные:
   - название;
   - подзаголовок;
   - описание;
   - keywords;
   - support URL;
   - Privacy Policy URL;
   - screenshots;
   - review notes.
10. Заполните App Privacy по готовому отчёту.
11. Заполните возрастную анкету по всему приложению, а не только child mode.
12. Не выбирайте Kids Category автоматически.
13. Заполните export compliance по готовому encryption report.
14. Проверьте PrivacyInfo.xcprivacy и Required Reason API report.
15. Загрузите archive/build официальным Apple-способом.
16. Выберите правильный build для версии.
17. Добавьте stable review account, review Parent PIN и точные инструкции.
18. Если первый optional non-consumable активен:
    - создайте продукт;
    - добавьте metadata;
    - добавьте review screenshot;
    - убедитесь, что sandbox работает;
    - добавьте первый non-consumable к отправке вместе с новой версией.
19. Проверьте release method:
    - рекомендуется manual release для первой версии.
20. Нажмите `Add for Review`.
21. Проверьте draft submission.
22. Только после последней сверки нажмите `Submit for Review`.

По официальной процедуре Apple сначала выбирается build, затем версия
добавляется в draft submission через Add for Review, после чего отдельно
нажимается Submit for Review. Первый non-consumable соответствующего типа
нужно отправлять вместе с новой версией приложения.

11. GOOGLE PLAY — ЧТО СДЕЛАТЬ
======================================================================

1. Войдите в Play Console.
2. Проверьте тип аккаунта и верификацию владельца/организации.
3. Проверьте Android developer verification и регистрацию package/signing.
4. Убедитесь, что package name окончательный.
5. Убедитесь, что приложение установлено как PAID до первого публичного
   production release.
6. Никогда не публикуйте этот package публично бесплатно как beta.
7. Завершите Google Payments Profile.
8. Задайте цену и SAFE_INITIAL countries.
9. Проверьте Play App Signing и upload key.
10. Загрузите точный AAB сначала в internal/closed testing.
11. Выполните тестирование, которое требует именно ваша Play Console.
    Для некоторых новых personal accounts Console может потребовать
    закрытое тестирование до production access; ориентируйтесь на
    фактическое требование в аккаунте.
12. Заполните App content:
    - Privacy Policy;
    - Ads = No;
    - App Access;
    - Target audience;
    - Content rating;
    - Data Safety;
    - Permissions;
    - Account deletion — если аккаунт включён.
13. Укажите stable reviewer credentials и Parent PIN без OTP/SMS.
14. Проверьте Families Policy, поскольку есть осознанный детский режим.
15. Создайте один optional non-consumable, если он включён.
16. Проверьте:
    - реальную цену;
    - sandbox/test purchase;
    - server verification;
    - pending;
    - acknowledgement;
    - Restore;
    - refund/revocation.
17. Проверьте Pre-review checks и pre-launch report.
18. Устраните все P0/P1.
19. Создайте production release.
20. Проверьте Publishing overview.
21. Оставьте controlled/manual publishing включённым, если это помогает
    сохранить контроль над первой датой выхода.
22. Отправьте изменения на review.
23. Не запускайте rollout до итоговой проверки approval/status.

Критически важно: приложение, однажды публично предложенное бесплатно в
Google Play, нельзя просто вернуть в paid status под тем же package name.
Поэтому paid status проверяется до первого production release.

12. RUSTORE — ЧТО СДЕЛАТЬ

5. Выберите тип приложения `Платное`.
6. Задайте цену.
7. Проверьте package name.
8. Проверьте signing certificate/fingerprint.
9. Загрузите точный подписанный APK или AAB.
10. Убедитесь, что version code больше предыдущего для обновления.
11. Заполните:
    - название;
    - категорию;
    - возрастное ограничение;
    - краткое описание;
    - полное описание;
    - минимальную Android-версию;
    - контакт разработчика;
    - icon;
    - реальные screenshots.
12. Заполните User Data Safety.
13. Если обнаружены dangerous permissions, объясните назначение либо
    удалите разрешение. Для V12 опасные разрешения по умолчанию не нужны.
14. Добавьте комментарий модератору:
    - stable account;
    - Parent PIN;
    - child mode path;
    - store/Restore path;
    - offline path;
    - объяснение paid Base Edition;
    - отсутствие Disney/Pixar.
15. Подключите текущий RuStore Pay flow для optional product.
16. Проверьте server verification и восстановление.
17. Убедитесь, что RuStore variant не содержит:
    - Google Play links;
    - App Store links;
    - Google Play Billing;
    - предложение обновиться в другом магазине.
18. Сохраните черновик и дождитесь обработки файла.
19. Повторно откройте черновик и проверьте все поля.
20. Нажмите `Отправить на модерацию`.

RuStore поддерживает APK и AAB. Подпись и package должны сохраняться для
обновлений. В текущей инструкции RuStore также требует реальные mobile
screenshots, данные безопасности и цену для paid app.

Для первой версии рекомендуется manual release. Staged release RuStore
используйте для последующих обновлений, когда эта возможность применима.
