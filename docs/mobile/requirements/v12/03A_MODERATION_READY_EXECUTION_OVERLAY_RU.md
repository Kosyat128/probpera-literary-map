# V12 MODERATION-READY EXECUTION OVERLAY
# HIGHEST PRIORITY BINDING CONTRACT

This document overrides any older instruction that conflicts with store
moderation readiness. It does not weaken the existing site-first, paid-app,
child-safety, rights, security, performance or three-platform contracts.

======================================================================
1. IMMUTABLE PRODUCT FOUNDATION
======================================================================

The existing «Литературная планета» on probpera.ru and the actual current
repository main are the only canonical foundation.

Codex MUST reuse the actual current:

- LiteraryGlobe and globe scene;
- GlobeCameraRig and camera-intent system;
- geography, projection, picking, highlights and country focus;
- globe edition registry and texture/provenance pipeline;
- MuseumSkyDome, MuseumStarfield, atmosphere and lighting;
- country, writer, work/book and Nobel datasets;
- verified biography pipeline;
- canonical real portrait and SVG flag pipelines;
- CMS/admin publication and evidence systems;
- brand logo, orange/violet palette, typography and owner locks.

A second globe engine, copied mobile literary database, AI-generated real
writer portrait, fake flag, invented biography, remote website as primary
WebView runtime, or divergent country coordinates is a P0 release blocker.

======================================================================
2. STORE IDENTITY AND NAME
======================================================================

Default store-facing identity:

- App name: «Литературная планета»
- Subtitle/tagline where supported: «Проба пера»
- Publisher/brand: the verified legal owner of probpera.ru / «Проба пера»
- In-device display name: «Литературная планета», unless an official
  platform length or collision requires an owner-approved localized form.

Do not use an over-30-character title. Do not call the app “official”
unless the developer account and rights evidence prove that claim.
Do not include Disney, Pixar or other licensed marks in the base app name,
subtitle, keywords, icon or screenshots before explicit marketing rights.

The app icon, installed name, store name, splash identity and support
documents must be mutually consistent.

======================================================================
3. TARGET AUDIENCE AND AGE-RATING STRATEGY
======================================================================

The default product strategy is:

“An educational literary application for a general/family audience with
a separately protected child mode.”

Do NOT automatically enroll the entire iOS app in Apple’s Kids Category.
That is an owner/legal/store decision after reviewing the final binary,
metadata, SDKs, external links, advertising absence and future update
obligations.

The age rating applies to the whole submitted binary, not merely child
mode. The review package must disclose potentially mature themes present
in adult biographies or works, including violence, war, death, suicide,
substance use, sexuality, illness, political repression or other sensitive
material where applicable.

Google Play target-audience declarations must match the actual child-facing
experience. The app may target mixed ages only if all child-directed
surfaces, SDKs, data practices, ads absence and parental gates satisfy the
current Families requirements.

RuStore age marking and content declarations must match the actual
application and screenshots.

Create a store-by-store age-rating worksheet from the exact release
candidate. Never choose the lowest rating merely because child mode is
filtered.

======================================================================
4. REVIEWER ACCESS AND TESTABILITY
======================================================================

Every store reviewer must be able to test the entire relevant product
without:

- personal SMS;
- one-time email code;
- physical biometrics;
- owner intervention;
- geo-restricted internal network;
- expiring credentials;
- production payment;
- hidden undocumented gestures.

Provide a stable review account or deterministic review mode when account
features exist. It must not bypass child-safety or purchase logic in
production; it may use sandbox products and a review-only configuration
that is cryptographically/environment gated and absent from normal public
navigation.

Reviewer materials must include:

- exact route to child mode;
- non-expiring review Parent PIN;
- route to adult store;
- route to Restore Purchases;
- sandbox product behavior;
- offline mode instructions;
- graphics Economy fallback;
- account deletion path;
- explanation that the base app is paid;
- exact contents of Starter Set;
- disclosure that Disney candidates are excluded unless licensed;
- any backend or region dependency;
- contact that can respond promptly.

Automated precheck must prove the review credentials work from a clean
installation and from a different network.

======================================================================
5. RIGHTS-CLEAN RELEASE BINARY
======================================================================

The exact release candidate (RC) APK/AAB/IPA/PWA artifact must be scanned for:

- unlicensed Disney/Pixar names where prohibited;
- Disney/Pixar logos;
- film/cartoon frames;
- protected character artwork;
- unauthorized music, voice or 3D models;
- marketplace or fan-art assets without sublicensable rights;
- AI imitations of protected characters;
- generated portraits of real writers;
- unapproved book covers;
- images lacking provenance;
- expired licenses;
- hidden but bundled blocked assets;
- test keys, receipts or private source material.

A record marked BLOCKED/HIDDEN is not enough if its protected asset is
still bundled. Unlicensed assets must be absent from the production
artifact and production content manifest.

Every factual visual asset must have source, rights status, attribution,
territory/platform scope where needed, checksum and editorial approval.
When a writer portrait is unavailable, use the canonical faceless brand
placeholder.

======================================================================
6. SCREENSHOT AND METADATA TRUTH
======================================================================

Store screenshots and previews must be captured from the exact signed or
release-candidate build submitted for review, using real data and real
functionality.

The owner concept collage is documentation only and MUST NOT be submitted
as a store screenshot.

Store materials must not show:

- future features;
- mock prices;
- Disney or other licensed content not present in the build;
- generated writer faces;
- fake book covers;
- screens unavailable to reviewers;
- UI from a different platform or old version;
- misleading claims such as “№1”, “best”, “official” or guaranteed child
  outcomes without evidence;
- competitor store badges/links in another store’s submission.

If optional purchases are shown, screenshots and copy must clearly
distinguish:

- included in paid base app;
- optional purchase;
- already owned;
- unavailable/territory limited.

Create screenshots for the required device sizes from deterministic seeded
states and retain source captures, build SHA, content version and
post-processing log. Only cropping, device framing and permitted
annotations are allowed; do not alter product functionality in the image.

======================================================================
7. PRIVACY, DATA SAFETY AND ACCOUNT DELETION CONGRUENCE
======================================================================

Generate one canonical data inventory from source code, native manifests,
network calls, backend schemas, analytics/crash SDKs, purchase providers,
secure storage, child profiles and support tooling.

From that inventory produce:

- Apple privacy declarations/privacy manifest;
- Google Play Data Safety answers;
- Google Play target-audience and Families answers;
- RuStore privacy/permissions declaration;
- in-app Privacy Center;
- public privacy policy;
- account deletion page;
- reviewer privacy notes.

All declarations must match the exact release artifact. A NoOp analytics
provider is preferred until a third-party SDK is justified and audited.

If an adult account can be created, deletion must be initiable in-app and
through the required public web path. Deletion must remove or anonymize
server data within documented timelines and explain lawful retention.
Local child profiles must be deletable by the parent without creating a
child account.

Do not claim “we collect no data” if IP addresses, purchase verification,
crash logs, account identifiers or support requests are processed.

======================================================================
8. MINIMUM PERMISSIONS
======================================================================

Default requested permissions:

- network access;
- platform billing where implicit;
- secure storage/files required by app sandbox.

Do not request camera, microphone, contacts, SMS, phone, precise location,
broad storage, advertising identifier, background location or unrelated
notifications.

Narration is playback and does not require microphone permission.
If a future capability requires a sensitive permission, add it only after:

1. owner-approved feature;
2. user-visible just-in-time explanation;
3. platform declaration;
4. child-safety review;
5. denial-path functionality;
6. store moderation evidence.

Create a binary/manifests permission diff gate for every release.

9. PAID APP AND OPTIONAL PURCHASE MODERATION
======================================================================

Distribution remains:

PAID_UPFRONT_WITH_OPTIONAL_NON_CONSUMABLES

Before first public Google Play release, confirm the app is configured
PAID. Never use a public free listing as beta.

For App Store, the required paid-app agreement, banking/tax setup and

configured and price supplied.

The paid Starter Set must be complete and independently valuable. Child
mode, Parent Center, Планетка, core literary archive, search, included

Optional purchases must:

- use the platform-required purchase mechanism;
- expose real localized price;
- support pending, cancellation, restore, reinstall, refund and revocation;
- be server verified;
- not be advertised to a child;
- be absent or clearly unavailable when rights/territory do not permit;
- have review-accessible sandbox configuration.

Do not include a “buy cheaper on website” digital-content link in native
store builds unless current platform/territory rules explicitly permit it
and the final legal/store review approves it.

14. REJECTION AND RESUBMISSION WORKFLOW
======================================================================

When a store sends a rejection:

1. Preserve the exact original message, rule number, screenshots and
   metadata snapshot.
2. Classify: code, metadata, rights, access, privacy, audience, payment,
   stability, account, policy ambiguity or false positive.
3. Reproduce on the submitted build.
4. Create one tracked remediation issue.
5. Fix the root cause, not merely the reviewer-facing symptom.
6. Add regression test.
7. Update declarations/screenshots/notes if needed.
8. Generate a new build number and artifact checksum.
9. Re-run the complete affected store gate.
10. Respond factually and respectfully, pointing to the exact path and
    change.
11. Never conceal functionality or temporarily disable a rule-breaking
    path only for review.
12. Preserve the rejection ledger for future releases.

Codex must generate draft responses but the owner performs the actual
store communication and submission.

======================================================================
16. V12 MODERATION DEFINITION OF DONE
======================================================================

V12 moderation readiness is COMPLETE only when:

- real store-facing app name is within current limits;
- legal/publisher identity is consistent;
- target audience and whole-binary age disclosures are complete;
- Kids Category is not selected automatically;
- review access works without owner intervention;
- Parent Gate is testable;
- exact RC screenshots are truthful;
- concept collage is excluded from submission;
- no unlicensed assets are bundled;
- no generated real-person portrait is bundled;
- privacy declarations derive from actual data flow;
- account deletion is implemented where accounts exist;
- permissions are minimal and declared;
- paid-app state is configured or isolated as an objective external
  console blocker;
- optional IAP sandbox and server verification are ready;
- all release variants are store-clean;
- current SDK/target requirements are satisfied;
- technical review smoke passes;
- all three review dossiers are complete;
- rejection/resubmission playbook is tested;
- only objective external actions remain.

Store approval can never be guaranteed by code alone. The required result
is a complete, truthful, stable, legally supportable submission package
that minimizes preventable rejection risk.
