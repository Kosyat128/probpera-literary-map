# D252 — grant-only client Retry-After

Frozen external proposal based on clean D251 documentation HEAD `eb3384e75a7d5894d0ccc7434e7f24c79521348b`; unchanged application originals come from `1430890a33e360e272da74943b17415d70575ef3`. Seven existing owners, three production files and four affected suites. `manifest.json` binds original/proposed SHA-256 rows, twenty selected unchanged dependencies and all eight real SQL setup witnesses. Only `supabase/schema.sql` lies outside the existing conservative source roots.

The verified gap is the existing signed-grant client treating HTTP 429 as network failure and issuing another grant fetch on every manual check. D251 already supplies the durable server budget. This change preserves that authority and adds a transient wait in the individual client with an immutable issuer/audience/product/subject context. It adds no global or persisted quota, automatic retry, timer, API, database change or provider configuration.

Only an active, unredirected response from the exact configured grant endpoint can impose a wait. The canonical D251 contract supplies an integer delta of 1–86400 seconds. [RFC 9110 section 10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after) defines delta seconds relative to receipt of the response; the client therefore uses a millisecond deadline sampled after receipt, without flooring away a subsecond delay. Missing, malformed, merged, date and out-of-range headers return `rate-limited` without inventing a wait. A foreign or redirected response returns `invalid-response`, without setting a wait or deleting saved signed bytes. Current generation/abort checks precede mutation; no delayed old response can impose a later wait.

Online checks inside the deadline do not fetch. Offline checks still verify the signature, exact context and signed expiry/offline deadline; an offline check does not erase the server-requested wait. Real revocation/session-denial/cache invalidation remains unchanged. At the deadline a new manual check may fetch again. The existing access controller explicitly treats `rate-limited` as a temporary online failure and independently checks saved proof under the existing signed time limits. Without proof it uses accurate RU/EN retry-later copy. It never treats 429 itself as authorization or revocation.
