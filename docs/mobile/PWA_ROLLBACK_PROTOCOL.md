# Controlled PWA rollback preparation

This S03 implementation supports an explicit rollback of the verified application bootstrap to the immediately preceding activated generation. It is local preparation evidence, with `releaseReady: false`. The installed service-worker JavaScript engine remains current. Reverting that engine binary requires a separate server-served worker update and is not claimed as an offline capability.

The builder may anchor only an existing contained preparation artifact with the same normalized public authority fingerprint and the same explicit QA mode. It reads and verifies each prior bootstrap file against both its manifest and inventory. Legacy artifacts without that fingerprint, a different ephemeral QA authority, a different mode, an incomplete package, or a changed file cannot become an anchor. `license-authority.json` contains only the public authority or `null`; a private JWK or signing permission is rejected.

`bootstrap-integrity.json` may contain `rollbackReference: { buildId, manifestSha256, routes }`. The reference is bundled into the new worker, not downloaded as mutable configuration. Its sorted, unique exact routes contain the prior manifest paths and version aliases. They allow synchronous classification of an old hashed module after a service-worker process restart. `rollback-manifest.json` preserves the prior normalized configuration and its authority identity for independent artifact auditing.

Hash encoding is UTF-8 with lowercase hexadecimal SHA-256:

- The public authority is recursively sorted by object key, retains array order, and is serialized with compact `JSON.stringify`, without a trailing newline. Its hash is `authoritySha256`; the default authority is the JSON value `null`.
- `normalizePwaWorkerConfig` is the shared pure normalizer. Top-level field order is `schemaVersion`, `scopePath`, `buildId`, `entrypoints`, `files`, then optional `rollbackReference`. Entrypoints are optional `root`, then `ru`, `en`. Files sort by exact URL; file fields are `url`, `bytes`, `sha256`, `kind`, `aliases`, with sorted aliases, including an empty array. Reference fields are `buildId`, `manifestSha256`, `routes`. The manifest fingerprint hashes compact `JSON.stringify` of that normalized value without a newline.
- Build identity hashes `JSON.stringify(value, null, 2) + '\n'`, where fields occur in this order: `sourceCommit`, `sourceInputsSha256`, `workerSourceSha256`, `authoritySha256`, `localQaAuthority`, `authoritySource` (exact `{path, sha256}` or `null`), `rollbackReference` (explicit `null` when absent), `files` (the builder bootstrap records). The source-input snapshot uses the independently documented sorted source list and the same pretty JSON newline convention.

An ordinary configured preparation is built with `node scripts/mobile/build-pwa.mjs --authority configuration/public-authority.json`. The exact JSON file must be inside the checkout without symlinks or junctions and at most 16 KiB. It supplies only `issuer`, `audience`, `product` and one `trustedKeys` entry `{kid, jwk}`. The JWK must be a valid public P-256 curve point usable for ES256 verification. The builder records the source path and exact byte hash, rechecks it before replacing the local artifact, and the auditor checks current source bytes again. This flag does not set the QA constant, include a scene probe, allow insecure loopback licensing, start a signer or authorize deployment. It retains HTTPS-only same-origin identity/session endpoints and all release prohibitions.

`--qa-authority .tmp/pwa-qa/authority.json` is a mutually exclusive local QA option. It enables the existing loopback-guarded probe and explicit local HTTP fixture behavior. A QA artifact requires `--allow-qa` at audit time. Reusing the same public key across both modes does not permit a rollback from an ordinary artifact into a QA artifact. With neither flag, authority and authority source are both `null`, and paid access remains unconfigured and closed. `releaseReady` and `productionActionsAuthorized` remain false in all three preparation modes.

`PLANET_ROLLBACK_STATUS` accepts a bounded request ID from an exact same-origin configured shell WindowClient, including the canonical state query and fragment. Optional `engineBuildId` must match when supplied. The response reports `engineBuildId`, `activeBuildId`, and either a verified `rollbackBuildId` with `ready: true`, or `null` with `ready: false`. Discovery never changes selection or reloads a page.

`PLANET_ACTIVATE_ROLLBACK` additionally requires exact `engineBuildId` and `targetBuildId`. The worker requires the anchored previous COMPLETE marker's activation sequence to be exactly current minus one, verifies every prior byte and executable MIME, and rechecks the authorized client. It rejects other already-open controlled app windows. Cache selection is persisted before success is acknowledged. A failed validation or failed selection write preserves the current generation; there is no automatic rollback on a network error.

Navigation and resource replies have a generation fence around asynchronous work. While selection is being committed, new app navigation replies fail closed. This includes a late window created after the initial window-count check. Previously started resource replies cannot return current-generation bytes after the selection changes. A successful rollback shell binds its browser-supplied `resultingClientId` to the selected generation before returning the HTML. Subsequent assets require that binding, including across worker restarts. An older or unidentified document therefore receives an error rather than resources from another generation. Persisted document metadata is bounded to 128 entries; stale entries may be removed to admit a new navigation. These records establish document consistency and are not a licensing authority.

The controller exposes stable `rollback`, `activeBuildId`, and `engineBuildId` snapshot fields and an explicit `rollback()` method. It verifies worker identity, origin, request, target and acknowledgement before reloading once. This reload follows the rollback acknowledgement because changing the selected application cache does not produce `controllerchange`. Normal worker updates still require their separate acknowledgement and controller change. Cancellation cannot undo a selection already committed by the worker, and does not trigger a late automatic reload.

For the sequence A → B → explicit rollback A → update C, an artifact anchored only to B cannot advertise B as the previous app: the app preceding C was A. The worker retains the intact A cache and suppresses that incorrect rollback target. A transitive C → A rollback requires a separately bound lineage protocol; it is not inferred from mutable selection metadata.

The guaranteed offline rollback surface is the verified bootstrap: neutral/RU/EN shells, their essential module closure, default canonical assets, exact aliases and core catalog interfaces. Optional content outside that surface is not turned into an installed package by rollback. Child packages, audio, commercial entitlement reconciliation and a general download manager require their respective stage evidence. RU/EN action text remains explicitly marked draft until bilingual editorial approval.
