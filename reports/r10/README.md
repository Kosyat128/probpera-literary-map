Проверка файла и локального интерфейса не обозначается как production acceptance.

**Исполняемые пути.** `refresh-literary-news.yml` -> `sync-literary-news.mjs` -> ограниченный collector -> единое KV-поколение -> очередь существующей админки. Public Worker -> production selector -> полный snapshot -> существующий `LiteraryNewsPanel`. `publish-literary-news.yml` -> подтверждённый live snapshot -> admission/job reconciliation -> атомарный dispatch -> сохранённый receipt. Публикация исходного HTML и создание отдельных страниц новостей отсутствуют. Генерация AI и платные сервисы не подключались.

**Эксплуатация.** Источники и свежесть доступны в раскрываемой части повестки; очередь и доставка - в существующей `/literary-news` админке. Там же показаны точные тексты, ошибки, remote URL, пауза/возобновление и ручное разрешение неопределённого результата. Закрепления редактируются в существующем homepage editor. Для предварительного просмотра: `node scripts/publish-literary-news.mjs --preview-local`; реальных отправок эта команда не выполняет. Для повторной проверки дат: `node scripts/enrich-calendar-dates-r10.mjs --check`. Партия добавляется командой `node scripts/apply-literary-news-batch.mjs --batch=data/news/batches/r10-01.json --write`; повтор идемпотентен, `--rollback` снимает только неизменённые записи этой партии.

Затем заполняют проверенные назначения в `data/news/social-destinations.json`, сверяют прежнюю историю, проходят off -> shadow -> согласованный одиночный canary -> on. Отдельные переменные `LITERARY_NEWS_RUNTIME_ENABLED` и `LITERARY_NEWS_SEND_ENABLED` по умолчанию не включены; выпуск витрины или дат их не включает. Перед восстановлением старого backup необходимо остановить отправку внешними flags, учесть уже начатые запросы, оставить восстановленные каналы paused/shadow и сверить более свежие receipts и remote IDs. Старое значение `historyReconciled=true` не заменяет новую сверку; автоматического определения старого backup нет. Пауза канала сохраняет историю.
