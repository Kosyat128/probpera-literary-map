# Bounded Telegram release operator

Prepared workflow: `operate-literary-news-release.yml`. It is manual, main-only, binds the exact current main SHA, and shares `literary-agenda-delivery` concurrency with the scheduler. The only workflow destination is Telegram `-1002791579809` / `probbaperra`. VK `-231377018` remains off; CLI mutations for VK are explicitly rejected while its setup is deferred. Neither workflow nor real provider writes were executed during local development.

The code-owned approval in `data/news/social-release-approvals.json` must contain verified bot ID, chosen canary identity, reviewed observed-public-history evidence, and a validity interval of at most seven days. History includes its raw audit SHA, semantic-review SHA, page URL/hashes, observed ID range/count, and exact news identity/semantic-revision pairs. `newsHistoryCandidates` builds those pairs with the existing semantic revision function. `newsSocialPayloadDigest(approval.history)` is the digest required by actions. An approved review covers observed accessible posts only: deleted/private content is not inferred absent. The operator never manufactures this approval.

Run `inspect` first, using main SHA and the fixed canary ID `kokila-jason-reynolds-lamplighters-son-acquisition-2026`. The artifact gives exact prepared caption/text, image metadata, payload SHA, history digest, current control row version, and current provider identity/rights. It is explicitly nonsendable, makes no journal writes, uploads nothing, and publishes nothing. Missing storage/schema/credentials remain blocking errors.

`enable-canary` accepts only a previously absent destination control (expected version 0), exact history/payload digests and the reviewed canary ID. It verifies current public snapshot, rights, unchanged public channel head, and history coverage of all existing expectations. It captures the complete snapshot through the existing reconciler, then creates the canary control with one versioned CAS. A racing initializer or pause cannot be overwritten. Capturing expectations is not sending them.

`send-canary` requires the exact control row version reported by inspect/enable, plus the same history and payload digests. It rechecks current rights, history, current payload and public head, reconciles current admissions, and calls the existing durable dispatcher for that single job. The transport wrapper also checks the approved revision/payload/provider account and the same control version immediately before writing. Existing rights, pause, cooldown, lease, atomic dispatch-start fence, durable media upload cache and ambiguity rules remain in force. An acknowledged canary returns its existing remote identity without another send. It cannot unpause a channel, change the canary, reset an ambiguous result or create an edit implicitly.

`promote` requires the durable accepted canary receipt for exactly that revision/payload/bot/destination. The operator supplies its exact remote ID, `https://t.me/probbaperra/<remoteId>` and `native_viewed: true` after checking the actual native appearance. This declaration is recorded in the protected control journal, with action, repository SHA and workflow actor/run ID; it is not an automatic visual-approval claim. The workflow independently reads the exact public post and compares the full caption/text (whitespace normalized). If an approved image was prepared, it also requires that image in the native post; if no image was available, exact text alone is valid under the owner's text-fallback instruction. It rechecks the channel head, allowing only that known canary beyond the original audited maximum. Unknown intervening posts, missing/mismatched public proof, withdrawals, pending unknown historical jobs or ambiguous jobs block promotion. The successful CAS changes mode to `on`; enabling scheduler variables is a separate root release action.

`pause` needs only the current exact control version and storage. It retains existing mode, canary, approval and rights information. It does not fetch a feed or call a provider. Requests already started retain the established dispatcher behavior.

All workflow inputs are ordinary environment values, never interpolated shell code. Arbitrary destination IDs and endpoint URLs are not accepted. The ten workflow inputs respect GitHub's dispatch limit. API credentials appear only in existing secret environment bindings; receipts contain public content and small runtime metadata.
